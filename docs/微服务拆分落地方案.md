## 1. 背景与目标

### 1.1 背景

当前仓库是 RAGFlow fork，内含三类代码：

- **A 类（自有资产）**：`agent/langgraph/**`、`api/v1/**` —— LangGraph 编排层与 FastAPI 后端，与上游零血缘；
- **B 类（Canvas 层二开）**：`agent/component/` 下 grader / hallucination_detector / query_rewriter / hyde / sub_query_decomposer / retry_controller —— 全部为本团队新增文件（git 证据：commit `d0062c9`、`6b45249`），随 Canvas 引擎存留；
- **C 类（上游核心区补丁）**：`rag/nlp/t2s.py`、`rag/nlp/lang_detect.py`、`api/utils/chunk_preprocessor.py`、索引管线挂钩、schema 映射 —— 繁简双文本能力，物理上必须留在 RAGFlow 侧。

### 1.2 目标

将系统拆分为两个独立开发、独立部署、独立伸缩的微服务：

| 服务 | 角色 | 内容 |
|---|---|---|
| **ragflow-service** | 数据面 | 文档解析、双文本索引、混合检索、rerank、知识库/模型配置管理面（含现有管理 UI）、Canvas 遗留流程 |
| **agent-service** | 控制面 | LangGraph 编排（意图路由/SQL Agent/ReAct/Skill/Report）、质量裁判、幻觉检测、反思质检、会话与租户管理（api/v1 + web-new） |

### 1.3 非目标（Out of Scope）

- 不引入 LangChain（LLM 抽象、Tool 协议维持现状 JSON action 协议）；
- 不建设独立模型网关服务（采用共享模型客户端库方案，见 §2 D2）；
- Canvas 引擎退役不在本期范围（B 类组件随 ragflow-service 存留养老）；
- 三层幻觉检测反哺 LangGraph 节点列为后续独立工单，不阻塞本期（C12 禁止夹带）；
- 上游贡献（繁简双文本 PR）并行推进但不阻塞本期，见 §10；
- **provider 适配器从 `rag/llm/` 物理抽包**不在本期范围（见 §5.2 两阶段策略）。

## 2. 架构决策记录（ADR）

| 编号 | 决策 | 理由 | 已否决方案 |
|---|---|---|---|
| D1 | 不引入 LangChain，保持自研薄客户端 + JSON action 协议 | 与 harness-heavy 架构一致；LangChain 抽象与自有层全面重叠；`langchain` 包本就未被 import | 顺势迁移 LangChain（零收益、全链路回归风险） |
| D2 | **不独立模型网关服务**；agent-service 使用共享 `model-client` 库，模型配置经 ragflow-service 薄只读 API 解析 + 本地缓存 | 现阶段消费者仅 2 个；避免新增服务运维成本与故障单点。**注意：这不是"RAGFlow 零改动"，准确表述为「RAGFlow 模型管理体系零改造（LLMBundle/管理 UI/配置表结构不动），仅新增一个只读配置解析 API」** | LiteLLM Proxy 独立网关（作为未来演进项，触发条件见 §11.1） |
| D3 | **ragflow-service API 二次开发，检索响应暴露 `original_text` / `original_lang`** | 实测成本极低（见 §6.1 代码证据）；检索端点不透传 `fields` 参数，故必须改默认字段列表 | chunk_id 回查（多一次 IO，无必要）；接受简体文本（破坏繁体保真）；给端点加 `fields` 透传（改动面比直接加默认列表大，见 §6.1 备选分析） |
| D4 | **编排拓扑、状态字段、条件边、verdict 语义、预算护栏、降级语义冻结**；允许为依赖反转替换 LLM/Retriever 的**获取方式**（DI 接口替换） | 编排是最有价值的资产；但 model-client 化必然触碰 8 个调用点所在文件，必须精确界定"零改动"的边界是语义而非文本 | 借拆分顺手重构编排（范围蔓延）；完全不碰任何节点文件（与 D2 自相矛盾） |
| D5 | 绞杀者模式分阶段落地，每阶段可独立回滚 | 风险控制 | 大爆炸式切换 |
| D6 | 禁止共享数据库：任何服务不得直连对方 DB | 微服务基本红线 | 双服务直连同一 MySQL |
| D7 | 质量裁判/幻觉检测归属 agent-service；ragflow-service 仅保留检索执行 | 裁判需要全局上下文与处置权（详见职责矩阵 §4.1） | 智能检索 API（裁判下沉 ragflow-service） |
| D8 | 模型配置的**单一事实源**为 ragflow-service 的租户模型配置；`api/v1/model_configs` 表维持现状用途（api/v1 自身业务的模型登记），本期**不与 model-client resolver 集成**，其 `synced_to_ragflow` 同步机制的整合列为后续决策点（§11.4） | 避免双事实源；现有 `synced_to_ragflow` 表明 api/v1 本就以 RAGFlow 为下游 | 双源合并查询（优先级规则复杂且易错） |
| D9 | **agent-service 独立部署边界**：本期以「独立源码目录 + 独立容器镜像 + 独立 pyproject」实现，**provider 适配器代码按需要裁剪拷贝进 `packages/llm-runtime/`**（受控 fork，仅保留生产在用 provider），不再运行时依赖 ragflow 源码树；物理抽回原 `rag/llm/` 到独立 pip 包列为 Stage C（§11.1 触发） | 两阶段策略的 Stage B 若仍路径依赖 `rag/llm/`，agent-service 无法真正独立发布；受控拷贝比全量抽包便宜一个量级，且裁剪面可控（P0-5 已盘点生产 provider 清单） | 本期即全量物理抽包（范围爆炸，见 §1.3 非目标）；运行时发现缺 provider 才补（交付不可控） |

### 4.2 契约 1：检索 API（ragflow-service 提供）

**端点**：`POST /api/v1/retrieval`

> 路径依据（已核实代码）：`api/apps/__init__.py` L271-275 的 blueprint 注册逻辑——
> `api/apps/sdk/` 下文件统一挂载 `/api/{API_VERSION}` 前缀，`api/apps/sdk/doc.py`
> L1561 注册 `/retrieval` 路由，合成 `POST /api/v1/retrieval`。
> 实施时仍须以 curl 实测确认（见附录 A PR-1.1 验收）。

**请求参数**（基于 `doc.py` L1644-1751 实际支持的入参，★为客户端必须显式传值项）：

```json
{
  "question": "如何退貨",
  "dataset_ids": ["kb_xxx"],
  "★similarity_threshold": 0.2,
  "★vector_similarity_weight": 0.5,
  "rerank_id": "rerank_xxx",
  "top_k": 1024,
  "page": 1,
  "page_size": 5,
  "document_ids": null,
  "metadata_condition": null,
  "cross_languages": [],
  "keyword": false,
  "use_kg": false,
  "toc_enhance": false,
  "highlight": false
}
```

**⚠️ 关键参数映射（防漂移红线）**：

| agent-service（`RAGToolInput`） | ragflow-service（API） | 关系 |
|---|---|---|
| `similarity_threshold`（默认 0.2） | `similarity_threshold` | 同义直传 |
| `keywords_similarity_weight`（默认 0.5） | `vector_similarity_weight` | **`vector_similarity_weight = 1 - keywords_similarity_weight`** |
| `top_k`（默认 5） | `page_size`（页大小）+ `top_k`（截断上限） | 见下方说明 |
| `rerank_id` | `rerank_id` | 同义直传 |
| `kb_ids` | `dataset_ids` | 同义直传 |
| `cross_languages` | `cross_languages` | 同义直传；服务端会调 LLM 扩展查询 |

- `vector_similarity_weight` 的 **API 默认值是 0.3**，与我方进程内默认（0.5）不同——
  **客户端必须永远显式传值，禁止依赖服务端默认值**（否则远程模式检索行为系统性漂移）；
- 进程内 `settings.retriever.retrieval` 的 `size` 参数对应 API 的 `page_size`；API 的
  `top_k`（默认 1024）是截断上限。映射：`page_size = top_k(RAGToolInput)`，`top_k` 保持默认 1024；
- `cross_languages` 在**服务端**执行（`doc.py` L1729-1730 调 `cross_languages()`），
  远程模式下 agent-service 的 `RAGTool` 步骤 1（跨语言扩展）应跳过本地执行，
  仅透传参数（`HttpRetrieverGateway` 内处理该差异，见 §5.1 实现约束）。

**响应结构**（⚠️ v2.1 修正：真实 envelope 是 `get_result()` 包装，**业务数据在 `data` 键下**，
已核实 `api/utils/api_utils.py` L310-330 与 `doc.py` L1786）：

```json
{
  "code": 0,
  "data": {
    "total": 12,
    "chunks": [
      {
        "id": "chunk_xxx",
        "content": "<检索文本（即 content_with_weight 重命名）>",
        "original_text": "<★新增：原文文本（繁体保持繁体）>",
        "original_lang": "<★新增：zh-traditional | zh-simplified | en>",
        "document_id": "doc_xxx",
        "document_keyword": "退货流程.docx",
        "dataset_id": "kb_xxx",
        "similarity": 0.42,
        "important_keywords": [],
        "questions": [],
        "...": "其余现有字段不变"
      }
    ],
    "doc_aggs": {}
  }
}
```

失败响应（同构 envelope，`data` 键缺省）：

```json
{ "code": 102, "message": "`dataset_ids` is required." }
```

**Envelope 与错误码映射（`HttpRetrieverGateway` 实现依据，v2.1 新增）**：

- 成功判定：HTTP 200 **且** `code == 0`；业务数据一律从 `data` 键解包（`total/chunks/doc_aggs` 在 `data` 内）；
- `code != 0` 时按 `RetCode` 映射错误类型（枚举值以 `api/settings.py` 的 `RetCode` 为准）：

| 条件 | Gateway 异常 | 说明 |
|---|---|---|
| HTTP 401/403，或 `code` 为认证错误（AUTHENTICATION_ERROR=109） | `RetrievalAuthError` | 不重试，告警（API Key 失效/越权） |
| HTTP 400，或 `code` 为数据错误（DATA_ERROR=102，如 dataset_ids 非 list、embedding 不一致、kb 无权限） | `RetrievalDataError` | 不重试，业务错误透传 |
| HTTP 429 | `RetrievalServiceError`（重试） | 限流，指数退避 |
| HTTP 5xx / 连接错误 / 超时 | `RetrievalServiceError`（重试后仍失败则抛出） | 服务异常 → 降级链 |
| 熔断开启 | `RetrievalCircuitOpenError` | 不发起请求 |

**请求参数红线（v2.1 新增）**：`document_ids` / `cross_languages` / `dataset_ids` 等 list 参数
**禁止传 `null`**——服务端 `doc.py` L1675-1676 对非 list 的 `document_ids` 直接返回数据错误。
客户端序列化规则：**list 参数空时传 `[]` 或省略该字段，二选一并在实现中统一（建议：省略）**。

> 透传机制（已核实代码）：`doc.py` L1780-1784 响应层对 chunk **逐字段透传**（仅做
> key 重命名，无白名单过滤），L1765-1766 仅 `pop("vector")`。因此 `original_text`
> 进入检索结果后即自动出现在响应中，API 响应层**零改动**。

**契约约束**：
- 只增不改：不得删除/重命名/改变现有字段语义；
- `original_text` 仅当文档索引时已启用双文本才存在；消费方必须实现 fallback：`original_text ?? content`；
- 响应中的 `original_text` / `original_lang` 不经 key 重命名，原名出现；
- `search_text` 默认不返回（无消费场景；如需调试走 ES 直查，不为此扩 API）；
- payload 体积影响：繁体文档 chunk 文本量约翻倍，`HttpRetrieverGateway` 须按
  `page_size ≤ 20` 限制单次请求（当前 `top_k=5`，余量充足）。

### 4.3 契约 2：模型配置只读 API（ragflow-service 新增，★补丁 2）

`GET /internal/v1/llm-config/resolve`

| 参数 | 说明 |
|---|---|
| `tenant_id` | 租户 ID（必填） |
| `llm_type` | `chat / embedding / rerank`（必填） |
| `llm_id` | 模型 ID（可选，缺省返回租户该类默认模型） |

响应：

```json
{
  "provider": "OpenAI-Compatible",
  "model": "qwen-plus",
  "base_url": "https://...",
  "api_key": "sk-...",
  "max_tokens": 8192,
  "extra": {}
}
```

错误响应（与成功响应同构的外层信封）：

```json
{ "code": 40401, "message": "model config not found", "data": null }
```

**契约约束**：
- 仅内网可达（网络层隔离）+ `X-Service-Token` 服务端令牌鉴权（与租户 API Key 不同体系）；
- 只读：不提供任何写操作；
- **安全红线**：
  - `api_key` 传输仅允许内网 + TLS；
  - 该端点响应体**禁止进入 access log / 网关日志 / APM 采样**（实施时在日志中间件加路径黑名单）；
  - 消费方对 `api_key` 使用 SecretStr 等价物（禁 `str` 类型传递），禁止落盘、禁止进日志（含异常堆栈中的 locals  dump）；
  - 端点实现必须支持 **Key/模型即时失效语义**：`is_active=false` 或已删除的配置返回 404，不得因自身缓存返回旧值；
- 可用性要求：允许故障——消费方本地缓存兜底（见 §5.2 缓存策略），该 API 不追求高 SLA。

### 4.4 契约 3：agent-service 内部数据格式（不变）

`rag_docs`（`RAGToolOutput.docs`）格式**保持不变**：

```json
{"content": "<original_text 优先>", "score": 0.42, "source": "...", "chunk_id": "...",
 "doc_id": "...", "doc_type": "...", "status": "...", "metadata": {}}
```

远端 chunk → `rag_docs` 的映射在 `RetrieverGateway` 内完成，**下游所有节点（prompt_assembly / evidence_fusion / reflection / quality_check / report）零感知**。

字段映射表（`HttpRetrieverGateway` 实现依据）：

| rag_docs 字段 | 远端 chunk 字段 | 说明 |
|---|---|---|
| `content` | `original_text ?? content` | 原文优先，fallback 检索文本 |
| `score` | `similarity`（若无 rerank 分） | 与进程内 `_format_docs` 取分逻辑对齐 |
| `source` | `document_keyword` | |
| `chunk_id` | `id` | |
| `doc_id` | `document_id` | |
| `doc_type` / `status` / `metadata` | 同名字段 | 缺失给默认值 |

### 5.1 RetrieverGateway（检索网关接口 + HTTP 实现）

```python
class RetrieverGateway(Protocol):
    async def retrieve(
        self, *, query: str, kb_ids: list[str], tenant_id: str,
        top_k: int, similarity_threshold: float,
        keywords_similarity_weight: float, rerank_id: str | None,
        cross_languages: list[str] | None,
    ) -> dict:  # 返回与 settings.retriever.retrieval 同构的 kbinfos（含 chunks/doc_aggs）
        ...
```

**实现约束（AI 编码时必须遵守）**：
- `LocalRetrieverGateway`：包装现有 `settings.retriever.retrieval` 调用，**逐行保持原逻辑**（含 embedding 模型加载、KB 校验、本地 cross_languages）；
- `HttpRetrieverGateway`：
  - 参数映射严格按 §4.2「关键参数映射」表执行；
  - **本地 cross_languages 步骤跳过**，将 `cross_languages` 透传 API（服务端执行）；
  - 本地 KB 校验/embedding 一致性断言删除——服务端已做，错误透传为 `RetrievalDataError`；
  - rerank：只传 `rerank_id`，**本地不再调 `multilingual_rerank`**；
  - 响应 chunk → kbinfos 映射按 §4.4 表执行，`original_text ?? content` fallback；
- HTTP 客户端：**必须 `httpx.AsyncClient`**（禁止 `requests` 同步阻塞 async 节点），连接池复用（每实例上限 100）；
- 认证头：`Authorization: Bearer {tenant_ragflow_api_key}`（按租户从 `tenant_ragflow_credentials` 表取，见 §5.4）；
- **韧性要求**：
  - 超时：连接 3s / 读取 15s（环境变量可配，见 §5.6）；
  - 重试：仅对 429/5xx/超时重试，指数退避 2 次（0.5s/1.5s），总额外耗时 ≤ 2s；401/403/404/数据错误不重试；
  - 熔断：连续 5 次失败熔断 30s（进程内滑动窗口实现，不引入外部组件）；
  - **故障语义区分**：「服务异常」（超时/5xx/熔断）≠「检索为空」——前者抛 `RetrievalServiceError`，由 `RAGTool` 转空结果并打标 `retrieval_degraded=true` 写入 state，`quality_check` 据此直接 `fallback_web` 而非 `retry_rag`（重试一个挂掉的服务无意义）；
- **trace 传播**：请求头 `X-Trace-Id: {state.trace_id}`；客户端记录 `retrieval_remote_ms` 进 `node_timings`。

**错误分类（`agent/langgraph/gateways/errors.py`）**：

- 计量埋点全量记录（含 stale 命中标记），供审计。

### 5.7 组合根与每租户运行时注入（v2.1 新增，P1-4 落地设计）

**问题**：现有 `get_rag_tool()` / `get_sql_agent_runner()` 是进程级单例，而模式开关
（`local/remote/shadow`）与检索凭证都是**每租户**维度——单例构造期绑定实现会导致
租户级开关无法生效、凭证串租户。

**设计：解析发生在每次调用，而非构造期。**

```python
# agent/langgraph/gateways/factory.py
class GatewayResolver:
    """进程级单例：持有全部 Gateway 实现与配置缓存，按请求参数路由。"""

    def __init__(self):
        self._local_retriever = LocalRetrieverGateway()
        self._http_retriever = HttpRetrieverGateway(...)      # 内置凭证读取（按 tenant_id 查 §5.4 表）
        self._shadow = ShadowRetrieverGateway(self._local_retriever, self._http_retriever)
        self._runtime_config_cache = TTLCache(ttl=60)         # tenant_runtime_config 缓存

    async def retriever_for(self, tenant_id: str) -> RetrieverGateway:
        cfg = await self._runtime_config(tenant_id)           # 租户级覆盖 > 全局 env 默认
        mode = cfg.retrieval_mode or settings.RETRIEVAL_MODE
        return {"local": self._local_retriever,
                "remote": self._http_retriever,
                "shadow": self._shadow}[mode]
```

**约束**：
- `RAGTool.__init__` 接收 `resolver: GatewayResolver | None`（默认取进程级单例 resolver），
  `invoke()` 内每次执行 `resolver.retriever_for(tenant_id)`——**模式与凭证按请求解析**；
- `tenant_runtime_config` 变更经 60s 缓存收敛，**无需重启**；PR-1.5 验收按此执行
  （替换 v2.0「或明确需重启」的模糊表述）；
- `HttpRetrieverGateway` 不在构造时持凭证；每次请求按 `tenant_id` 查 §5.4 凭证表
  （60s 缓存），凭证缺失/失效 → `RetrievalAuthError`；
- `ModelGateway` 同理：`resolver.model_for(tenant_id)` 按 `model_mode` 选
  `LLMBundleAdapter` / `HttpConfigResolver` 实现 / shadow 包装；
- 4 个 RAG 调用入口（§5.9）全部经 `RAGTool`，故只需在 `RAGTool` 一处接入 resolver。

### 5.8 降级状态契约（v2.1 新增，P1-5 落地设计）

**问题**：v2.0 要求写 `retrieval_degraded=true` 入 state，但 `AgentState` 无此字段且 D4
冻结 state；同时 `RAGTool.invoke` 现状 catch 一切异常返回空结果，会吞掉
`RetrievalServiceError` 的错误语义。

**决策（D4 的显式增列，属 DI 替换必须的配套，不算语义变更）**：

1. `AgentState` 新增两个字段（TypedDict `total=False`，向后兼容）：

```python
# agent/langgraph/state.py 新增
retrieval_error_code: str | None   # RETRIEVAL_SERVICE_ERROR / RETRIEVAL_TIMEOUT /
                                   # RETRIEVAL_CIRCUIT_OPEN / RETRIEVAL_AUTH / None
retrieval_mode_used: str | None    # local / remote / shadow（观测用）
```

2. `RAGTool.invoke` 异常处理改为**分类捕获**：

| 异常 | 行为 |
|---|---|
| `RetrievalServiceError` 及子类（超时/5xx/熔断） | 转空结果 + 写 `retrieval_error_code`，**不打 error 日志堆栈**（warn 即可，熔断期避免刷屏） |
| `RetrievalAuthError` | 转空结果 + 写 `retrieval_error_code=RETRIEVAL_AUTH` + error 日志（配置问题需告警） |
| `RetrievalDataError` | 透传抛出（业务错误，如 KB 无权限——与现状 `raise Exception("No dataset is selected.")` 同语义，不静默） |
| 其他未知异常 | 维持现状：error 日志 + 空结果（不写 error_code） |

3. `rag_tool_node` 将 `retrieval_error_code` / `retrieval_mode_used` 从 `RAGToolOutput`
   透传入 state（`RAGToolOutput` 同步增列两字段）；
4. `quality_check_node` 决策前置规则（在 `_make_decision` 之前）：
   `retrieval_error_code in (RETRIEVAL_SERVICE_ERROR, RETRIEVAL_TIMEOUT, RETRIEVAL_CIRCUIT_OPEN)`
   → **直接 `fallback_web`**（重试挂掉的服务无意义）；
   `RETRIEVAL_AUTH` → `fallback_web` + 告警（重试无意义且属配置故障）；
   无 error_code → 走现有质量阈值决策（**既有 verdict/阈值逻辑零改动**）。

### 5.9 RAG 调用入口参数传递矩阵（v2.1 新增，P2-9 落地设计）

RAG 检索共 **4 个调用入口**，参数来源与缺口如下（★ = 现状未传、本期必须补齐的参数）：

| 参数 | ① `rag_tool_node.py` | ② `tool_dispatcher._execute_rag` | ③ `react/executor._call_rag_tool` | ④ `skill_rag.prepare` |
|---|---|---|---|---|
| `query` | `state.user_question` | `step.args.query` → state 兜底 | `arguments.query` | skill target 渲染 |
| `kb_ids` | `state.kb_ids` | `step.args.kb_ids` → state 兜底 | `arguments.kb_ids` → 构造参数兜底 | `target["kb_id"]`（skill 锁定） |

| `similarity_threshold` | ★ **现状未传**（恒用默认 0.2） | ★ 经 extra 可传 | ★ 现状未传 | ★ 现状未传 |

**补齐规则（PR-0.2 范围，行为对齐优先级）**：

1. **参数来源优先级**（4 入口统一）：`step.args.extra` / `arguments`（调用方显式指定）
   > skill target 声明 > `agent_config.rag_config` > 内置默认值；
2. ① `rag_tool_node` 必须从 `agent_config.rag_config` 读取并传入
   `similarity_threshold`、`keywords_similarity_weight`、`rerank_id`（现状遗漏属缺陷，

3. **远程模式独有约束**：`HttpRetrieverGateway` 收到 `rerank_id` 后仅透传 API；

4. 影子 diff 比较时，**两路径必须使用完全相同的 `RAGToolInput`**（由 resolver 在
   shadow 包装内复制输入，禁止各自从 state 二次组装——否则 diff 无意义）。

### 7.1 影子模式定义（实现约束）

- **主路径**：`local`（进程内实现），用户响应永远来自主路径；
- **影子路径**：`remote` 在后台异步执行（`asyncio.create_task` + 独立异常捕获），
  **任何影子失败不影响用户响应**，仅记 warn 日志；
- **采样**：按 `tenant_runtime_config.shadow_sample_rate`（默认 0.1）决定本次请求是否双跑；
- **diff 存储**：`retrieval_shadow_diff` / `model_shadow_diff` 记录（表结构由实施 PR 定义，
  至少含 trace_id、tenant_id、模式、主结果摘要、影子结果摘要、diff 指标、耗时）；
- **检索 diff 指标**（全自动）：top5 chunk id 集合、top20 id 包含率、分数差分布、
  original_text 在场率、P50/P95 延迟差；
- **模型 diff 指标**（全自动）：成功率、错误类型分布、finish_reason、token 计数差、
  延迟差；**输出文本一致性不作自动断言**（LLM 输出天然不稳定）——
  语义一致性仅作人工抽检（每周抽样 20 条），不进 DoD。

### 7.2 检索影子验收分层标准（替代 v1.0 的单一 99%）

| 层级 | 场景 | 标准 |
|---|---|---|
| L1 | 同索引、同参数（显式传 §4.2 映射参数） | top5 chunk id 完全一致（顺序允许 rerank 抖动 ±1 位） |
| L2 | 同索引、同参数 | top20 id 包含率 ≥ 95% |
| L3 | 分数比较 | `abs(local_score - remote_score) < 1e-6`（同 scorer 口径）；**禁止跨口径比较**（local rerank vs remote rerank 分数分布不同属预期，只比 id 集） |
| L4 | `original_text` 在场率 | 双文本索引文档 = 100%；存量未重建索引文档走 fallback，不纳入断言 |
| L5 | bad case | L1/L2 未达标的 case 全量人工复核，定位是参数映射、字段缺失还是引擎差异 |

### 7.3 API 归属与兼容矩阵（v2.1 新增，P1-7 落地设计）
