# 用户输入到报告输出：面试版讲解

> 目标：用通俗语言把整条链路讲清楚，可直接用于面试回答。
> 主线一句话：**先判意图 → 再决定查知识库/查数据库/并行多工具 → 拿证据 → 反思质检 → 生成答案 → 防幻觉核验 → 输出答案或报告**。

---

## 一、开场总述（30 秒版）

> 用户提问进来后，系统先做语言处理和意图路由：简单问题直接走单工具（查知识库或查数据库），复杂问题走 Planner 拆成多步骤并行执行。拿到证据后，先做一轮 LLM 反思和质量检查，不够就回退重试或降级 Web 搜索。证据够了才交给 LLM 生成答案，生成完还要过一道幻觉校验，不合格可以重新生成。最后如果任务带「报告」属性，还会走一套带 claim、血缘、人工审核、验证导出的治理管线，输出可下载报告。

---

## 二、分阶段通俗讲解

### 1. 入口与意图路由：先搞清楚「用户到底想要什么」

- **语言预处理**  
  先判断问题是简体、繁体还是英文；繁体统一转简体，保证后面检索和查表匹配时语义一致。

- **三层意图路由（快→慢递进，能快就不慢）**  
  1. **前置过滤（<1ms）**：像「你好」「查一下 XX 表」这种显式指令、敏感内容，直接定结果。
  2. **规则路由（<10ms）**：关键词打分，**置信度 ≥ 0.7 就直接拍板**，不再麻烦大模型。
  3. **LLM 语义路由（<300ms）**：规则拿不准时上大模型判断意图；如果模型觉得信息不够，还会主动反问用户澄清。
  4. **Planner（<5s）**：只有判断为**复杂任务**时，才把任务拆成一张 DAG 计划（比如「先查库 A 拿销量，再查知识库拿口径，最后生成报告」）。

- **Skill 解析**  
  如果问题带「报告 / 技能」语义，会先解析出对应的 ReportSkill / DataSkill / RetrievalSkill，把业务模板、证据要求、查询模板一起带进计划里，保证后面生成报告时按规范来。

---

### 2. RAG 流程：查知识库拿到靠谱资料

- **查询优化**  
  先做跨语言扩展（可选）、繁简转换，再做查询重写（同义词扩展等），复杂策略目前简化为同义词，留待接 LLM。

- **混合检索**  
  同时用 **BM25（关键词）+ 向量（语义）** 检索，阈值 0.2、关键词权重 0.5，保证既抓字面又抓语义。

- **Rerank 精排**  
  如果配置了重排模型，再对候选结果做一次精排，把最相关的排到前面。

- **质量评估 + 内部重试**  
  分数 ≥0.5 才算相关；如果一条相关都没有，或相关少于 2 条，会**换一种重写策略自动重搜一次**，避免因为一次检索失败就放弃。

---

### 3. DB 流程：让 Agent 自己去「探库」

> 这里已经从「固定规则查库」升级成「SQL Agent 自主探索」。

- **三种走法按优先级：**
  1. **结构化模板**：如果命中治理好的查询模板（比如固定报表口径），直接执行参数化 SQL，**零 LLM 调用**，最快最稳。
  2. **SQL Agent 探索（默认）**：让大模型像人一样分步操作——
     - 先看有哪些库（`list_databases`）
     - 再看库里有哪些表（`list_tables`）
     - 再看表结构（`describe_table`）
     - 最后生成 SQL 执行（`execute_sql`）
  3. **legacy 规则**：只作为应急回滚，平时不走。

- **安全与成本护栏**
  - 有**预算上限**：最多 10 步、10 次 LLM、4 次 SQL 执行、90 秒，超了就强制收尾。
  - SQL 执行前会做 AST 校验、表白名单校验，**强制加 LIMIT**，防止全表扫描。
  - SQL 报错不会直接失败，而是把错误信息回给 Agent，让它**自己分析、修正、重试**。
  - 最后会给出一个明确的 verdict：`data_found`（查到数）/ `no_data_confirmed`（确认没数）/ `exploration_failed`（探索失败）/ `budget_exhausted`（预算耗尽），下游据此决定是放行还是重试。

---

### 4. 复杂任务：Plan Executor 并行多工具

- Planner 拆出的 DAG 计划会交给 **Plan Executor**：
  - 同层步骤**并行执行**（比如同时查库、查知识库、查 Web），不同层按依赖串行。
  - 每一步根据类型分发：查知识库走 RAG，查数据库走模板或 SQL Agent，查 Web 走搜索，生成报告走 ReportTool。
  - 单步失败不影响其他步骤，最后统一聚合成 rag_docs / db_result / web_docs，保证下游格式一致。

- 还有一条 **受限 ReAct 子图**（默认关闭）：让 Agent 自主多步推理、调用工具，但全程有预算、权限、白名单护栏，产出的是标准 Evidence，再经过融合和充分性判断后才进入质检。

---

### 5. 反思与质检：先自查，再生成

- **Reflection（反思）**  
  把 RAG / DB / Web 的结果汇总，让 LLM 快速判断：信息够不够？缺什么？下一步该干嘛？如果 LLM 不可用，默认放行，**不阻塞主流程**。

- **Quality Check（质量检查）**
  - 查知识库：分数 ≥0.7 且相关 ≥2 条才算过。
  - 查数据库：根据 SQL Agent 的 verdict 决定——查到数或确认没数就放行；探索失败就重试；预算耗尽就降级 Web 搜索。
  - 不达标且还能重试，就回炉重查；彻底不行就降级 Web 搜索兜底。

---

### 6. 生成与核验：防幻觉兜底

- **Prompt 组装**  
  把 RAG 原文、数据库结果表格、Web 资料一起拼成最终 Prompt，喂给大模型。

- **LLM 生成**  
  大模型基于这些证据生成答案。

- **幻觉校验（Hallucination）**
  - 校验答案里的数字、事实是否和证据一致，给出忠实度分数。
  - 分数高直接过；中等放行但标记；偏低就**重新生成（最多 2 次）**；实在太离谱就拒答，避免误导用户。

---

### 7. 报告生成：一条带治理的流水线

如果任务是「生成报告」，会走一条更严格的管线：

1. **校验证据**：证据不足直接拒绝。
2. **章节规划**：按报告类型或 Skill 模板规划章节。
3. **内容生成**：LLM 逐节生成，自动生成图表和表格。
4. **Claim 与血缘**：把报告里的关键数据声明（claim）和证据绑定，记录数据来源，方便追溯。
5. **人工审核评估**：财报、成本等敏感类型会标记为待人工审核。
6. **验证**：校验报告里的数字是否都能和证据对上，做敏感扫描；**验证不过直接拒绝导出**。
7. **导出**：只有通过审核的报告才有下载链接，草稿和待审核的只能查看不能下载。

最后报告结果会回到主链路，由 final_answer 统一输出为「报告已生成」或「报告生成失败」的结构化响应。

## 三、面试答题模板（可直接背）

> 我们这套系统的核心思路是「**先判意图，再拿证据，后生成，全程有质检和护栏**」。
>
> 1. **意图路由**：用「前置过滤 → 规则 → LLM → Planner」四层递进，简单问题毫秒级响应，复杂问题自动拆成多步计划。
> 2. **证据获取**：查知识库走「混合检索 + Rerank + 质量评估」，查数据库走「SQL Agent 自主探库」，支持模板短路和自愈重试。
> 3. **质量保障**：拿到证据后先做 LLM 反思和质量检查，不够就重试或降级 Web；生成答案后再过一道幻觉校验，不合格可以重新生成。
> 4. **报告治理**：报告类任务额外走「规划 → 生成 → claim → 血缘 → 人工审核 → 验证 → 导出」的管线，保证数据可信、可追溯。
>
> 整体设计上，我们既保证了简单查询的低延迟，又保证了复杂任务和报告场景的质量与安全性。

## 四、高频追问点速查

| 面试官可能问 | 可以这样答 |
|---|---|
| 怎么控制成本？ | 规则路由优先，LLM 只在必要时调用；SQL Agent 有步数 / LLM / SQL 执行 / 时间四重预算上限。 |
| 怎么防止 SQL 注入或危险操作？ | 所有 SQL 先过 AST 校验和表白名单，只允许 SELECT，强制 LIMIT，执行错误回传给 Agent 自愈。 |
| 检索质量怎么保证？ | 混合检索 + Rerank + 质量阈值；不达标自动换策略重搜；再不行降级 Web 搜索。 |
| 怎么防幻觉？ | 生成后做忠实度校验，分数低重新生成，最差拒答；报告还要过数字 ↔ 证据匹配验证。 |
| 复杂任务怎么并行？ | Planner 生成 DAG，Plan Executor 同层并行、层间串行，单步失败不影响整体。 |
