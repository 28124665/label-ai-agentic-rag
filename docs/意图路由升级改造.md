# 生产级意图路由改造 —— 需求规格说明书

> **项目名称**：鸿海集团 Agentic RAG 系统 —— 意图路由模块生产级改造
> **文档版本**：V1.0
> **编制日期**：2026-07-28
> **关联系统**：LangGraph Agentic RAG 系统（`agent/langgraph/nodes/intent_router.py`）
> **上游依赖**：`question_input` 节点
> **下游消费**：`rag_tool`、`db_tool`、`web_tool`、`prompt_assembly`


## 一、背景与目标

### 1.1 项目背景

当前 Agentic RAG 系统的意图路由完全由 `intent_router` 节点的**关键词规则**驱动：

```100:113:agent/langgraph/nodes/intent_router.py
if has_aggregation or has_entity:
    if has_concept:
        return "hybrid"
    return "database"

if has_concept:
    return "rag"

return "chitchat"
```

这套规则在系统快速验证阶段是合理的——零延迟、零成本，能覆盖约 60%-70% 的简单查询。但随着系统从“建设期”进入“瓶颈期”，用户开始提出更复杂的问题，单一的关键词路由开始显露疲态。

**核心矛盾**：试图用一套检索逻辑解决所有类型的问题，会导致系统在“过度设计”（资源浪费）和“能力不足”（回答错误）之间摇摆。一个生产级系统需要构建智能查询路由器，让系统根据用户意图的复杂度动态选择最合理的检索路径。

### 1.2 改造目标

将意图路由从**单一关键词规则**升级为**“规则优先 + LLM 语义路由 + Planner 复杂任务拆解”的三层递进架构**，实现：

1. **精准路由**：将用户问题精准分发至最合适的工具（RAG / DB / Web / Hybrid / Chitchat）
2. **语义理解**：识别关键词无法捕捉的隐含意图和同义表达
3. **复杂度感知**：区分简单事实查询与复杂多跳推理，动态分配模型资源
4. **可观测与可迭代**：路由决策可追溯、可评估、可优化


## 二、现状与问题

### 2.1 当前实现

| 维度 | 现状 | 问题 |
| :--- | :--- | :--- |
| **决策依据** | 纯关键词字符串匹配 | 无法处理语义歧义（“数据治理是什么”被误判为 hybrid） |
| **路由粒度** | 4 种固定路由（rag/db/hybrid/chitchat） | 无法识别“直接走 Web”的意图；无法拆解复合任务 |
| **置信度** | 无 | 低置信度时不会向用户澄清，直接盲目调用工具 |
| **复杂任务** | 无法处理 | “分析最近三个月质量异常的主因”只能走单一路由 |
| **成本感知** | 无 | 简单查询和复杂查询消耗相同模型资源 |
| **可观测性** | 仅记录路由结果 | 缺少路由原因、置信度、备选路由等诊断信息 |

### 2.2 典型 Bad Case

| 用户问题 | 当前路由 | 期望路由 | 失败原因 |
| :--- | :--- | :--- | :--- |
| “数据治理是什么” | hybrid（因含“数据”） | rag | 关键词误判语义 |
| “统计学原理是什么” | database（因含“统计”） | rag | 关键词误判语义 |
| “今天天气怎么样” | chitchat（无关键词命中） | web | 无法识别时效性需求 |
| “最近质量异常有改善吗” | chitchat | db（查趋势） | 无法识别隐含的数据查询意图 |
| “对比 A 产线和 B 产线的 OEE” | database（因含聚合词） | hybrid（RAG找定义+DB查数据） | 无法识别复合意图 |


## 三、总体架构

### 3.1 三层递进路由架构

```
用户问题
    ↓
┌─────────────────────────────────────────────────────────────┐
│  第0层：前置过滤（< 1ms，零成本）                            │
│  ─────────────────────────────────────────────────────────  │
│  • 安全拦截：SQL注入特征、越权关键词 → 直接驳回              │
│  • 显式指令：含“搜索/查一下”+“网上/百度” → web_tool          │
│  • 问候语：含“你好/谢谢” → chitchat                         │
│  • 实体格式：匹配 SKU- / ORD- 格式 → db_tool                │
└─────────────────────────────────────────────────────────────┘
    ↓（未命中前置规则）
┌─────────────────────────────────────────────────────────────┐
│  第1层：规则路由（< 10ms，零成本）【保留并增强】             │
│  ─────────────────────────────────────────────────────────  │
│  • 优化关键词库 + 增加范围词判断（内部/外部）               │
│  • 增加置信度打分（每个规则命中输出 confidence）             │
│  • 增加时效性检测（“今天/最新”且不含“去年” → web）          │
│  • 输出：intent + confidence + reason + entities           │
└─────────────────────────────────────────────────────────────┘
    ↓（confidence < 0.7 或 规则无法判定）
┌─────────────────────────────────────────────────────────────┐
│  第2层：LLM 语义路由（< 300ms，微成本）                     │
│  ─────────────────────────────────────────────────────────  │
│  • 模型：Qwen3.5-9B（独立部署）                             │
│  • 输出结构化 JSON：primary_intent + confidence +           │
│    complexity + sub_intents + entities + needs_clarification│
│  • confidence < 0.6 → 触发用户澄清                         │
│  • complexity = "complex" → 转交 Planner                   │
└─────────────────────────────────────────────────────────────┘
    ↓（complexity = "complex"）
┌─────────────────────────────────────────────────────────────┐
│  第3层：Planner 复杂任务规划（< 3s，高成本）                │
│  ─────────────────────────────────────────────────────────  │
│  • 模型：Qwen3.6-27B Dense                                 │
│  • 拆解多步任务 → 生成执行计划（DAG）                      │
│  • 识别依赖关系 → 标记可并行执行的子任务                    │
│  • 输出：plan（tool + args + depends_on 列表）             │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 与 LangGraph 的集成位置

```
question_input → 【意图路由（三层）】 → quality_check
                      ↓
            ┌─────────┼─────────┬──────────┐
            ↓         ↓         ↓          ↓
        rag_tool  db_tool  web_tool  prompt_assembly
                                      （chitchat）
```

路由输出作为 `AgentState` 的一部分，供后续 `quality_check` 节点消费。


## 四、详细需求

### 4.1 第0层：前置过滤

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
| :--- | :--- | :--- | :--- |
| **FR-00-01** | **安全拦截**：检测 SQL 注入特征（`'; DROP`、`--`、`UNION SELECT` 等）和越权关键词（“删库”、“所有用户密码”），直接驳回并记录审计日志 | P0 | 拦截率 100%，误拦截率 < 0.1% |
| **FR-00-02** | **显式外部搜索指令**：同时命中“动作词（搜索/查一下/上网找）”和“外部范围词（网上/百度/谷歌/外部/全网）”时，直接路由 `web_tool` | P0 | 命中率 > 95%，误命中率 < 1% |
| **FR-00-03** | **问候语识别**：匹配“你好/谢谢/嗨/hello”等问候模式，直接路由 `chitchat`（跳过检索，直接进入 Prompt 组装） | P1 | 命中率 > 98% |
| **FR-00-04** | **实体格式匹配**：匹配预定义的实体格式（如 `SKU-\d+`、`ORD-\d+`、`工单号：\d+`），直接路由 `db_tool` | P1 | 命中率 > 95% |

### 4.2 第1层：规则路由（保留并增强）

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
| :--- | :--- | :--- | :--- |
| **FR-01-01** | **范围词优先判断**：在判断聚合/实体/概念词之前，先判断查询范围——含“网上/百度/谷歌”标记为 `scope=external`，否则默认 `scope=internal` | P0 | 范围判断准确率 > 90% |
| **FR-01-02** | **聚合/实体词库优化**：扩充 DB 偏向词库，增加“多少、总额、占比、排名、TOP、环比、同比、最大值、最小值”等；区分“查询数据”与“查询定义”的语义差异 | P0 | 词库覆盖率达到业务高频查询的 85% |
| **FR-01-03** | **概念词库优化**：扩充 RAG 偏向词库，增加“定义、解释、含义、区别、联系、影响、原因、背景”等 | P0 | 词库覆盖率达到业务高频查询的 85% |
| **FR-01-04** | **置信度打分**：每个规则命中输出 `confidence` 分数（0-1），多条规则冲突时取最高分 | P0 | 置信度能有效反映规则匹配的确定性 |
| **FR-01-05** | **时效性检测**：命中“今天/最新/实时/current/latest/trending”且**未命中**“去年/历史/往年/过去”时，标记 `freshness_required=true`，路由建议为 `web`（或并行 web+内部检索） | P1 | 时效性查询的准确路由率 > 90% |
| **FR-01-06** | **规则配置化**：所有关键词库、优先级、置信度阈值通过 YAML/JSON 配置文件管理，支持热加载 | P1 | 配置变更无需重启服务即可生效 |

### 4.3 第2层：LLM 语义路由

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
| :--- | :--- | :--- | :--- |
| **FR-02-01** | **触发条件**：仅当第1层规则路由的 `confidence < 0.7` 或规则无法判定时，调用 LLM 语义路由 | P0 | 第2层触发率占整体请求的 20%-30% |
| **FR-02-02** | **模型选型**：使用 **Qwen3.5-9B**（或更小的 4B/2B 版本）独立部署，专门负责意图分类 | P0 | 单次推理延迟 < 300ms |
| **FR-02-03** | **结构化输出**：强制 LLM 输出 JSON 格式，包含以下字段：<br>• `primary_intent`: database \| rag \| web \| hybrid \| chitchat<br>• `confidence`: 0.0-1.0<br>• `reason`: 简短的路由理由<br>• `complexity`: simple \| moderate \| complex<br>• `sub_intents`: 子意图列表（如 ["aggregation", "temporal_filter"]）<br>• `entities`: 提取的关键实体（如 `{"metric": "产量", "time": "Q3"}`）<br>• `needs_clarification`: true \| false<br>• `clarification_question`: 如需澄清时的追问话术 | P0 | JSON 解析成功率 > 99%；字段完整性 100% |
| **FR-02-04** | **置信度阈值与降级**：<br>• `confidence ≥ 0.75`：直接采纳路由结果<br>• `0.6 ≤ confidence < 0.75`：采纳但附带低置信度标签，供 `quality_check` 节点参考<br>• `confidence < 0.6`：不直接路由，触发用户澄清节点 | P0 | 低置信度触发澄清的比例控制在 5% 以内 |
| **FR-02-05** | **Prompt 模板管理**：路由 Prompt 遵循“定义明确、边界清晰、输出结构化”原则，支持版本管理和 A/B 测试 | P1 | 支持至少 3 个 Prompt 版本的并行对比 |

### 4.4 第3层：Planner 复杂任务规划

| 需求编号 | 需求描述 | 优先级 | 验收标准 |
| :--- | :--- | :--- | :--- |
| **FR-03-01** | **触发条件**：仅当第2层 LLM 路由输出 `complexity = "complex"` 时触发 | P1 | 第3层触发率占整体请求的 5%-10% |
| **FR-03-02** | **模型选型**：使用 **Qwen3.6-27B Dense**（或同等能力模型），专门负责复杂任务拆解 | P1 | 单次推理延迟 < 3s |
| **FR-03-03** | **执行计划生成**：输出结构化的执行计划（DAG），包含：<br>• `plan_id`: 计划唯一标识<br>• `steps`: 步骤列表，每步包含 `tool`、`args`、`depends_on`（依赖的前置步骤 ID）<br>• `estimated_tokens`: 预估 Token 消耗<br>• `fallback_strategy`: 某步失败时的降级方案 | P1 | 计划生成成功率 > 85% |
| **FR-03-04** | **并行标记**：识别无依赖关系的子任务，标记为可并行执行（如同时查 RAG 和 DB） | P2 | 并行标记能有效减少复杂任务的端到端延迟 |

## 六、技术方案

### 6.1 模型部署（配置占位即可）

| :--- | :--- | :--- | :--- | :--- |

### 6.2 第2层路由 Prompt 模板（参考）

```
# Role
你是一个智能系统的意图分类器。你的任务是将用户输入精准分类到预定义的意图类别中。

# Intent Definitions
[DATABASE]: 用户需要查询具体的业务数据、报表或进行统计分析。通常包含时间、指标和聚合需求。
  示例："上个月销售额是多少？"、"Q3 华东区总产量"、"SKU-1001 当前库存"

[RAG]: 用户询问关于产品功能、公司政策、操作规范等客观事实或概念解释。
  示例："质量规范是什么？"、"如何申请年假？"、"良率的定义"

[WEB]: 用户需要实时信息或超出内部知识库范围的公开信息。
  示例："今天天气怎么样？"、"最新的行业政策"、"马斯克最近在忙什么"

[HYBRID]: 用户问题同时涉及精确数据查询和概念/规范理解。
  示例："高端机型中利润最高的那款"（需RAG找定义+DB查数据）

[CHITCHAT]: 问候、闲聊或不属于上述类别的通用问题。

# Constraints
- 不要尝试回答用户的问题
- 仅输出 JSON，不要包含任何解释
- 输出格式：{"primary_intent": "...", "confidence": 0.0-1.0, "reason": "...", "complexity": "simple|moderate|complex", "entities": {...}, "needs_clarification": false}

# User Input
{{user_query}}
```

### 6.3 降级与容错

| 场景 | 降级策略 |
| :--- | :--- |
| 第2层 LLM 超时（> 500ms） | 降级到第1层规则路由结果 |
| 第2层 LLM 返回 JSON 解析失败 | 重试 1 次；仍失败则降级到第1层 |
| 第2层 LLM 连续失败 3 次 | 熔断，直接走第1层规则路由，持续 60 秒 |
| 第3层 Planner 超时（> 5s） | 降级到第2层路由结果（视为 moderate 复杂度） |
| 所有路由均无法判定 | 默认走 `rag_tool`（最安全），附带低置信度标签 |

## 八、风险与应对

| 风险 | 影响 | 概率 | 应对措施 |
| :--- | :--- | :--- | :--- |
| LLM 路由幻觉（将 DB 意图误判为 RAG） | 回答错误，用户信任度下降 | 中 | ①设置置信度阈值，低置信度时触发澄清 ②路由结果经 `quality_check` 二次验证 ③持续收集 Bad Case 优化 Prompt |
| LLM 路由延迟超标 | 用户体验下降 | 中 | ①设置超时降级（> 500ms 回退到规则） ②使用小模型（9B）而非大模型 ③缓存高频查询的路由结果 |
| 第3层 Planner 成本失控 | 单次请求 Token 消耗激增 | 低 | ①设置单次 Planner 调用预算（max_tokens=2048） ②仅 5%-10% 请求触发 ③复杂任务结果可缓存复用 |
| 规则与 LLM 路由结果冲突 | 路由决策不一致 | 低 | ①规则路由提供 baseline，LLM 仅在低置信度时介入 ②冲突时取置信度更高的结果 ③所有冲突案例记录到审计日志 |

*本需求文档对应的意图路由改造完成后，系统将从“关键词驱动的静态路由”升级为“规则+语义+规划的三层动态路由”，使 Agentic RAG 系统真正具备“审时度势”的智能决策能力。*
