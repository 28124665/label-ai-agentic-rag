## 一、背景与目标

### 1.1 问题

在鸿海（富士康）中高层管理场景中，系统需要支持 6 个领域知识库：

| 编号 | 知识库 | 目标用户 |
|------|--------|---------|
| KB-1 | 集团战略与经营管理库 | 集团高管、战略规划部门 |
| KB-2 | 产品与技术研发库 | 各事业群研发副总、技术总监 |
| KB-3 | 生产与品质运营库 | 各厂区厂长、制造/品质/工程主管 |
| KB-4 | 供应链与全球布局库 | 全球供应链主管、采购/物流总监 |
| KB-5 | 人力资源与组织文化库 | HR 副总裁、各事业部 HRBP |
| KB-6 | 数字化转型与创新库 | CTO、CIO、数字化转型办公室 |

这带来两个核心问题：

1. **权限控制**：不同用户对 6 个 KB 有不同的查询权限（如张总可查 KB-1/2/6，李总可查 KB-3/4/6），RAGFlow 原生 `me/team` 二元权限模型无法满足
2. **KB 选择**：用户提问时，是查所有有权限的 KB 还是只查相关的？全查可能引入噪音，路由选错可能漏检

### 1.2 设计目标

| 目标 | 描述 |
|------|------|
| 精细化权限 | 支持用户-KB 级别的访问控制，不同用户可查不同 KB 组合 |
| 不破坏原生 | 兼容 RAGFlow 原生 `me/team` 权限模型，新权限为增强而非替代 |
| 检索效率 | 默认全查保证召回，复杂场景按需选 KB 提升精度 |
| 可扩展 | 权限模型支持未来扩展到文件级、文档级权限 |

```python
def check_kb_team_permission(kb, user_id):
    if kb["tenant_id"] == user_id:       # 我是创建者 → 允许
        return True
    if kb["permission"] != "team":        # 非 team 模式 → 拒绝
        return False
    # team 模式：检查用户是否属于该租户
    joined_tenants = TenantService.get_joined_tenants_by_user_id(user_id)
    return any(t["tenant_id"] == kb["tenant_id"] for t in joined_tenants)
```

#### 2.1.4 原生模型的局限性

| 场景 | 原生支持？ | 说明 |
|------|-----------|------|
| 我创建的 KB 只有我能看 | ✅ | `permission=me` |
| 我创建的 KB 整个团队都能看 | ✅ | `permission=team` |
| 同一租户下，用户 A 能看 KB-1 但不能看 KB-2 | ❌ | 无此能力 |
| 按部门/角色分配 KB 访问权限 | ❌ | 无此能力 |
| KB 可见范围是"部分团队成员" | ❌ | 无此能力 |

### 2.2 方案设计：新增 `kb_user_permission` 表

#### 2.2.1 数据库设计

```sql
CREATE TABLE kb_user_permission (
    id           VARCHAR(32) PRIMARY KEY,
    kb_id        VARCHAR(32) NOT NULL,
    user_id      VARCHAR(32) NOT NULL,
    granted_by   VARCHAR(32) NOT NULL,
    create_time  DATETIME DEFAULT CURRENT_TIMESTAMP,
    update_time  DATETIME DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,

    UNIQUE KEY uk_kb_user (kb_id, user_id),
    INDEX idx_kb_id (kb_id),
    INDEX idx_user_id (user_id)
);
```

#### 2.2.2 权限判定规则（优先级从高到低）

```
1. kb.tenant_id == user_id          → ✅ 允许（KB 创建者，最高权限）
2. kb_user_permission 有记录        → ✅ 允许（显式授权）
3. kb.permission == "team"
   AND 用户属于 kb.tenant_id 的租户 → ✅ 允许（原生团队共享）
4. 其他                             → ❌ 拒绝
```

**设计要点**：
- 新表是**增强**而非替代：原生 `me/team` 逻辑仍然生效
- 显式授权优先于团队共享：即使 `permission=me`，只要白名单有记录就能访问
- 不需要 `permission` 字段新增枚举值，不破坏原生逻辑

```python
class KBPermissionService:
    """KB 用户权限服务"""

    @staticmethod
    def get_permitted_kb_ids(user_id: str) -> list[str]:
        """获取用户有权限访问的所有 KB ID。
        
        合并三个来源：
        1. 用户创建的 KB（tenant_id == user_id）
        2. 团队共享的 KB（permission == 'team' AND 用户属于该 tenant）
        3. 显式授权的 KB（kb_user_permission 表）
        """
        ...

    @staticmethod
    def filter_permitted_kb_ids(kb_ids: list[str], user_id: str) -> list[str]:
        """从给定的 kb_ids 列表中过滤出用户有权限的。
        
        Args:
            kb_ids: 待校验的 KB ID 列表
            user_id: 用户 ID
            
        Returns:
            过滤后用户有权限的 KB ID 列表
        """
        permitted = set(KBPermissionService.get_permitted_kb_ids(user_id))
        return [kb for kb in kb_ids if kb in permitted]

    @staticmethod
    def grant(kb_id: str, user_id: str, granted_by: str) -> bool:
        """授予用户对指定 KB 的访问权限"""
        ...

        """撤销用户对指定 KB 的访问权限"""
        ...

    @staticmethod
    def get_users_by_kb(kb_id: str) -> list[dict]:
        """获取指定 KB 的授权用户列表"""
        ...
```

```python
@staticmethod
def _extract_agent_resources(agent_config, user_id=None):
    tools_config = agent_config.get("tools_config", {}) or {}
    raw_kb_ids = list(tools_config.get("kb_ids", []) or [])

    # 权限过滤：只保留用户有权限的 KB
    if user_id:
        kb_ids = KBPermissionService.filter_permitted_kb_ids(raw_kb_ids, user_id)
        if len(kb_ids) < len(raw_kb_ids):
            logger.warning(
                f"User {user_id} lacks permission for KBs: "
                f"{set(raw_kb_ids) - set(kb_ids)}"
            )
    else:
        kb_ids = raw_kb_ids

    return kb_ids, db_id, llm_id
```

## 三、Part B：KB 选择策略

### 3.1 当前路由架构

当前系统有 4 层渐进式路由，决定**用哪个工具**（RAG/DB/Web），但**不决定查哪个 KB**：

```
Layer 0: PreFilter  → 安全拦截、指令检测、问候语
Layer 0.5: ComplexityGate → 复杂度判断
Layer 1: RuleRouter → 关键词模式匹配（强模式 confidence≥0.8，弱模式≤0.55）
Layer 2: LLMRouter  → LLM 语义路由（带熔断器）
Layer 3: Planner    → 多步推理计划生成
```

**关键事实**：所有路由层的输出 `RouteDecision` 只有 `target`（工具名），没有 `kb_ids`（KB 选择）。`kb_ids` 从 API 层直接透传到 RAG 工具，全程无过滤。

### 3.2 两种方案对比

| 维度 | 方案 A：路由选 KB | 方案 B：全查 |
|------|---------------------|--------------|
| 检索精度 | 高。不相关 KB 的噪音被提前排除 | 中。Rerank 能过滤大部分噪音，但无关 chunk 挤占 top_k 名额 |
| Token 消耗 | 低。只检索相关 KB | 高。多 KB 检索总量大，易触发压缩 |
| 容错性 | 低。路由错误 → 直接漏检 | 高。总会覆盖到正确答案 |
| 延迟 | 低。检索 KB 少 | 略高。向量检索本身很快，差异小 |
| 实现复杂度 | 高。需新增 KB 选择逻辑 | 零。现有架构已支持 |
| 跨领域问题 | 困难。如"数字化对供应链的影响"需 KB 4+6 | 天然支持 |

### 3.3 分阶段组合策略

**核心原则：能用 Rerank 解决的，不加路由；路由能显著提升效率的，才加。**

```
┌─────────────────────────────────────────────────────┐
│                    用户问题                           │
└─────────────────────┬───────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────┐
│  Step 0: 权限过滤                                    │
│  raw_kb_ids → KBPermissionService.filter → permitted │
└─────────────────────┬───────────────────────────────┘
                      │
                      ▼
┌─────────────────────────────────────────────────────┐
│  Step 1: 默认策略 — 全查（方案 B）                     │
│  简单问题 / 中等复杂度 → 传入所有 permitted kb_ids     │
│  理由：Rerank 能有效过滤，零路由风险                    │
└─────────────────────┬───────────────────────────────┘
                      │
                      ▼
              ┌───────┴───────┐
              │ 复杂度判断     │
              └───────┬───────┘
                      │
        ┌─────────────┼─────────────┐
        │ simple      │ moderate    │ complex
        ▼             ▼             ▼
   ┌─────────┐  ┌──────────┐  ┌──────────┐
   │ 全查    │  │ LLM 推荐 │  │ Planner  │
   │ 所有KB  │  │ kb_ids   │  │ 指定KB   │
   │ (方案B) │  │ (方案A)  │  │ (方案A)  │
   └─────────┘  └──────────┘  └──────────┘
```

### 3.4 场景详解

#### 场景 1：简单问题（全查）

```
用户：Q3 营收情况如何？
复杂度：simple
策略：全查所有 permitted kb_ids
原因：问题简单，Rerank 能轻松过滤非财务类 chunk
```

#### 场景 2：中等复杂度（LLM 推荐 KB）

```
用户：A 事业群 iPhone 产线良率最近三个月趋势如何？与 B 事业群对比？
复杂度：moderate
策略：LLM Router 推荐 kb_ids = ["kb_product", "kb_production"]
原因：跨领域但明确，LLM 能准确判断需要产品库 + 生产库
```

#### 场景 3：复杂问题（Planner 指定 KB）

```
用户：数字化转型对供应链成本的影响分析，以及建议的推进路线图
复杂度：complex
策略：Planner 生成多步计划
  Step 1: RAG → kb_ids=["kb_digital"] 查询 "数字化转型现状"
  Step 2: RAG → kb_ids=["kb_supply_chain"] 查询 "供应链成本结构"
  Step 3: DB → 查询近 12 个月供应链成本数据
  Step 4: REPORT → 综合分析 + 建议路线图
```

## 四、完整调用链

```
┌──────────────────────────────────────────────────────────────────┐
│  API Layer                                                        │
│  conversation_service.stream_response(user_id, agent_config)      │
│    → _extract_agent_resources(agent_config, user_id)              │
│      → KBPermissionService.filter_permitted_kb_ids(raw, user_id)  │
│        → 返回 filtered_kb_ids（权限过滤后）                        │
│    → runner.arun_stream(kb_ids=filtered_kb_ids)                   │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│  Agent Runner                                                     │
│  AgentState.kb_ids = filtered_kb_ids（初始全量）                   │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│  Intent Router                                                    │
│  simple → 不修改 kb_ids（全查）                                   │
│  moderate → LLM Router 推荐 kb_ids，写入 route_decision           │
│  complex → Planner 为每个 Step 指定 kb_ids                        │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│  RAG Tool Node                                                    │
│  route_decision.kb_ids 非空 → 使用推荐 kb_ids                     │
│  route_decision.kb_ids 为空 → 使用 state.kb_ids（全查）           │
└──────────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌──────────────────────────────────────────────────────────────────┐
│  RAGTool._retrieve(kb_ids)                                        │
│  LocalRetrieverGateway.retrieve(kb_ids)                           │
│  → 联合检索所有指定 KB，top_k=100，Rerank 到 top_k=20             │
└──────────────────────────────────────────────────────────────────┘
```

## 六、风险与预案

| 风险 | 影响 | 预案 |
|------|------|------|
| LLM Router 推荐 KB 错误 | 漏检相关 KB 的内容 | `kb_ids=[]` 时回退全查；Rerank 天然兜底 |
| Planner 指定 KB 不全 | 复杂问题的部分子问题缺信息 | Planner 输出中增加 `kb_ids_fallback` 字段 |
| 权限表数据量大 | 查询变慢 | `kb_user_permission` 在 `user_id` 和 `kb_id` 上建索引 |
| 原生权限与新权限冲突 | 用户可见 KB 与预期不符 | 新权限为增强（OR 逻辑），不会减少原可见范围 |
