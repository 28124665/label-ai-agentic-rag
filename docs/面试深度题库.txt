一、意图路由层（Q1-Q4）
================================================================

----------------------------------------------------------------
Q1. 意图路由是「前置过滤 → 规则 → LLM → Planner」四层递进。为什么
不让 LLM 直接路由所有请求？级联架构真正的收益是什么？
----------------------------------------------------------------
【考察点】能否讲清级联本质是「成本与不确定性递增的漏斗」，以及
可观测性/可控性收益。

【参考要点】
- 成本与延迟：前置过滤 <1ms、规则 <10ms、LLM <300ms、Planner <5s。
  线上大部分请求是简单/高频模式（问候、显式指令、明确关键词），
  用毫秒级确定性逻辑处理即可，不必为每个请求付一次 LLM 调用的
  钱和 300ms 延迟。
- 可靠性：LLM 路由失败/抖动只影响进入第 2 层的少数请求，确定性
  层天然是降级兜底。
- 可治理：规则和关键词可审计、可灰度、可回归测试；LLM 决策不可
  完全复现，应该只处理真正的语义模糊请求。
- 一句话：级联不是省 LLM，而是「把不确定性集中到最值得花钱的
  少数请求上」。


----------------------------------------------------------------
Q2. 规则路由置信度 ≥0.7 直接短路不上调 LLM。这个 0.7 怎么定的？
如果规则路由"自信地判错了"（把查库问题高置信度判成闲聊），系统
有什么机制发现？
----------------------------------------------------------------
【考察点】对级联架构最大盲区「规则假阳性」的认知；下游信号回流
校准的意识。

【参考要点】
- 0.7 来自配置（thresholds.rule_to_llm），是经验值，严谨做法应
  基于离线评估集调参：标注一批 query 的路由真值，画阈值-准确率
  曲线选点。
- 盲区本质：高置信误判不会再经过 LLM，错误在路由层就被"锁死"，
  是最危险的失败模式（比低置信危险，低置信至少会升级）。
- 发现机制（项目现状+可补充方向）：
  1) 下游信号：quality_check 失败率、retry_count 分布按
     route_decision.source 分桶统计——规则路由的 retry 率异常
     升高即预警；
  2) 用户负反馈（点踩/重问）与 route_source 关联；
  3) 影子路由：定期抽样让 LLM 对规则已判请求做 shadow 判定，
     比对分歧率；
  4) bad case 回流到规则关键词表/阈值调参。

Q3. needs_clarification 会进 clarification 节点，用户回答后回流
重新路由。第二轮路由看到的 user_question 是什么？原始问题和澄清
答案怎么拼接？直接覆盖会不会丢上下文？
----------------------------------------------------------------
【考察点】状态机回边（back-edge）与多轮上下文累积的处理细节。

【参考要点】
- 图结构上 clarification → intent_router 存在回边，state 中原始
  user_question 不被覆盖（LangGraph state 按 key 更新，未更新的
  key 保留）。
- 正确做法：澄清答案应作为增量信息累积（如 clarify_answers 列表
  用 reducer 追加），第二轮路由时将「原始问题 + 澄清问答对」拼成
  增强上下文再判意图，而不是只看最后一句话。
- 直接覆盖的风险：用户原始意图丢失（"查一下销量" → 澄清"哪个
  季度？" → 用户答"Q3" → 第二轮只剩"Q3"，路由彻底跑偏）。
- 项目现状：answerability 的 ask_clarification 当前不主动打断主
  流程（统一放行 quality_check），澄清与主干解耦，是后续增强点。


----------------------------------------------------------------
Q4. hybrid 模式下 rag_tool 和 db_tool 是串行的（rag → db），不是
并行。为什么？放弃了什么、换来了什么？
----------------------------------------------------------------
【考察点】对编排取舍的理解：延迟 vs 简单性/语义依赖。

【参考要点】
- 串行换来：
  1) 图结构简单——hybrid 复用「rag_tool 完成后经 after_rag_tool
     进 db_tool」一条条件边即可，状态合并不需要并行 reducer；
  2) 语义上 DB 侧可复用 RAG 产物（如业务口径、指标定义先由 RAG
     拿到），prompt 组装时两类上下文顺序固定；
  3) 失败定位容易，node_timings 线性可读。
- 放弃的：端到端延迟 = RAG 耗时 + DB 耗时（SQL Agent 预算上限
  90s，串行 worst case 明显拉长）。
- 演进方向：plan_executor 的 DAGScheduler 已支持同层并行，hybrid
  完全可以建模为「两个无依赖 PlanStep 的并行计划」，把串行让位给
  并行 + ResultAggregator；保留串行的理由只剩"图简单"时，就是该
  重构的信号。

二、SQL Agent（Q5-Q11）

----------------------------------------------------------------
Q5. 没有用模型原生 tool-calling，而是让 LLM 输出 JSON action 由
harness 解析分发。为什么不用 bind_tools？至少三个工程理由。
----------------------------------------------------------------
【考察点】「闭环黑盒 vs 单步原语」的本质权衡。

【参考要点】
1) 模型无关性：JSON 协议任何能输出文本的模型都能驱动，不被厂商
   tool-calling 能力/格式绑架；国产/开源模型 tool-calling 能力
   参差，JSON 协议兼容性最好。
2) 单步可拦截：harness 在 action 执行**之前**能做预算检查、
   PolicyGuard 权限校验、幻觉护栏；原生闭环（async_chat_with_tools）
   在 LLM 层内部一口气跑完循环，外部看不见也拦不住。
3) 可观测与可回放：每一步 action/observation/耗时进 step_trace，
   可审计、可重放、可定位；黑盒只返回最终文本。
4) 容错可控：JSON 解析失败 harness 给 2 次容错并把错误原因回传
   模型纠正；黑盒解析失败行为不可控。
- 代价：prompt 里要带工具协议说明（token 开销）+ 格式鲁棒性依赖
  解析器——这是为可控性付的税。


----------------------------------------------------------------
Q6. 预算五维：10 步 / 10 次 LLM / 4 次 SQL / 6 次 describe / 90s。
为什么 SQL 执行（4次）比 describe（6次）限额更紧？只保留一个维
度你留哪个？
----------------------------------------------------------------
【考察点】对"什么资源最稀缺/最危险"的排序。

【参考要点】
- SQL 更紧的原因：
  1) SQL 是对真实数据库的副作用操作——消耗 DB 连接/算力，错误
     查询可能扫大表影响线上；
  2) describe 是元数据读，成本低且有缓存（命中缓存不计预算）；
  3) 设计上鼓励"多看 schema、少出手执行"——探索用 describe，
     执行要克制。
- 只留一个：留墙钟时间 90s。因为它是唯一能同时约束所有资源的
  维度（步数/LLM/SQL 都消耗时间），直接对应用户可感知延迟的
  SLA 上限；其他维度都可能被"快但密集"的操作绕过。


----------------------------------------------------------------
Q7. SQL 报错不抛异常，而是作为 Observation 回传 Agent 自愈。这和
try-catch 重试的本质区别？Agent 会不会在同一错误上原地打转？
怎么防？
----------------------------------------------------------------
【考察点】错误语义化 vs 盲目重试；防打转机制。

【参考要点】
- 本质区别：try-catch 重试是"同一动作再来一次"，不利用错误信息；
  error-as-observation 让模型**读懂错误原因**（列名不存在 → 重新
  describe 确认 → 修正 SQL），是语义级自愈，重试的是"修正后的新
  动作"而不是旧动作。
- 打转风险真实存在，防线有三层：
  1) step_trace 含全部历史，模型能看到自己上次也这么错过
     （prompt 层抑制）；
  2) 预算硬约束：SQL 执行最多 4 次、总步数 10 步、90s 墙钟，
     打转必然撞顶（harness 层兜底）；
  3) 解析失败另有 2 次容错上限。
- 打转的最终出口：预算耗尽 → verdict=budget_exhausted →
  quality_check 判 fallback_web，不会无限循环。


----------------------------------------------------------------
Q8. describe_table 有"幻觉护栏"：表名必须在已披露的 list_tables
清单内。为什么需要？这个护栏把幻觉从"错误"变成了什么？
----------------------------------------------------------------
【考察点】把模型不可控行为转化为可校验前置条件的设计思想。

【参考要点】
- 必要性：LLM 会编造"看起来像"的表名（users_order、order_info），
  不拦截则每次假 describe 都打到 MCP/DB 层浪费预算，错误 schema
  还会污染上下文让后续 SQL 越写越错。
- 护栏位置：在 action **执行前**校验（harness 层），不消耗
  describe 预算。
- 幻觉被转化为：一次"可纠错的拒绝 Observation"——回传"该表不在
  已披露清单，请先 list_tables"，错误本身成为模型的导航信号。
- 一句话：好护栏不是挡死模型，而是把错误变成下一步的路标。


----------------------------------------------------------------
Q9. 决策总序「① 结构化模板 > ② TemplateMatcher > ③ SQL Agent >
④ legacy」。为什么确定性路径排在 Agent 前面？TemplateMatcher
误命中会发生什么？
----------------------------------------------------------------
【考察点】确定性优先的治理思想；模板误命中是最危险失败模式的
认知。

【参考要点】
- 确定性前置的原因：零 LLM 成本、毫秒级、SQL 经过治理审核
  （口径正确、可审计、可复现），对已知问法没必要让 Agent 重新
  探索一遍（探索本身有随机性）。
- 误命中的后果：模板 SQL 语法合法、能执行、返回**看似正常但语义
  错误的数据**——静默错误，比报错危险得多；且模板执行成功就不会
  fallback 到 Agent，错误直接进答案。
- 防线（现状+可补充）：
  1) 模板匹配规则应窄化（精确问法/关键词组合而非模糊匹配）；
  2) 模板版本治理与灰度发布；
  3) 监控：模板命中率、模板结果的下游质量分、用户负反馈；
  4) 报告链路的 verifier 数字↔证据校验是最后一道网；
  5) 注意区分：模板**执行失败**（SQL 报错）会放行给 Agent，但
     语义错误不会触发任何失败信号。

Q10. verdict 四态中 no_data_confirmed 被 quality_check 判 pass。
"没查到数据"为什么算通过？和 data_found 混为同一路径，LLM 生成
时怎么区分？
----------------------------------------------------------------
【考察点】pass 的语义是"结论可信"而非"有数据"。

【参考要点】
- pass 的含义：探索过程可信、结论有效。"确认无数据"和"查到数据"
  都是**有效结论**，都应该放行；该重试的是"探索失败"（结论不可
  信），该降级的是"预算耗尽"（没探完）。
- 若把 no_data 判失败：对天然无数据的查询会无意义重试到耗尽，
  最后还降级 Web 答非所问。
- 生成层区分：db_result.formatted_result 携带空结果与 verdict
  语义进 prompt，LLM 应如实生成"经查询，当前条件下无相关记录"，
  而不是硬编数字——这正是 verdict 存在的意义：给生成层一个
  "允许说没有"的授权。
- 反例：没有 verdict 时，空结果和探索失败在下游无法区分，只能
  一刀切重试或一刀切放行，两种都错。

Q11. 强制 LIMIT 注入（500）在 harness 层做，而不是写 prompt 让
模型自觉。为什么？COUNT(*) 这类聚合查询怎么办？
----------------------------------------------------------------
【考察点】「不信任模型自觉」原则；AST 层精细化的实现思路。

【参考要点】
- 为什么 harness 层：prompt 是软约束——模型可能忘、可能忽略、
  可能被用户提问诱导（"列出全部"）；harness 注入是硬约束，确定
  性生效，与模型行为无关。安全边界的价值恰恰在于不随模型变化。
- 聚合查询：LIMIT 对 COUNT(*)/SUM 等单结果集查询无害（结果就
  一行，LIMIT 500 不改变语义）；真正需要区分的是行扫描型查询。
- 实现层：sqlglot AST 解析后可以判断语句类型（是否聚合、是否
  已有 LIMIT、子查询结构），比字符串拼接安全得多，还能避免
  "已有 LIMIT 1000 时再注一个" 的冲突（应取 min 或尊重更小值）。
- 边界情况：用户真要全量导出——工具定位是分析查询不是导出，
  应明确拒绝或分页，而不是放开 LIMIT。

三、RAG 检索链路（Q12-Q15）
================================================================

----------------------------------------------------------------
Q12. 混合检索关键词/向量权重各 0.5。凭什么五五开？什么场景该调？
----------------------------------------------------------------
【考察点】两种检索信号的本质差异 + 评估驱动调参意识。

【参考要点】
- BM25 保精确匹配：专有名词、编号、SKU、法条编号、人名——向量
  对这些"字面敏感"查询天然弱；
- 向量保语义召回：口语化改写、同义表达（"怎么退钱" vs "退款
  流程"）——BM25 对措辞差异天然弱；
- 0.5/0.5 是无评估数据时的中立默认值，不是最优解；
- 调整方向：知识库以合同/法条/工单编号为主 → 提高关键词权重；
  以自由文本 FAQ/经验文档为主 → 提高向量权重；
- 正确姿势：建标注评估集（query → 相关 chunk），用 recall@k /
  nDCG 扫权重曲线选点，而不是拍脑袋。

Q13. 质量评估取分优先级 rerank_score > similarity > score，即开
不开 rerank 的分数混在同一阈值（0.5/0.7）下比较。两种分数同量纲
吗？有什么坑？
----------------------------------------------------------------
【考察点】评估指标一致性的敏感度（本题是真实缺陷候选）。

【参考要点】
- 不同量纲：rerank 模型输出与向量 cosine 相似度分布完全不同
  （rerank 分数常压缩在窄区间，相似度分布取决于模型和归一化方
  式），混用同一阈值 = 用体重秤量身高。
- 具体坑：
  1) 开关 rerank 后，同样的文档集合"是否相关"的判定会漂移——
     昨天 pass 的今天 retry；
  2) quality_check 的 0.7 阈值在两种口径下松紧不一，重试率
     不可比；
  3) 监控指标（质量分均值）在配置变更后出现假波动。
- 修复方向：按 scorer 分别校准阈值；或统一到同一分布（如
  min-max/分位数归一）；或评估只认一种口径（如统一用 rerank
  后分数，无 rerank 时跳过精排阈值走另一套）。

Q14. 内部重试只 1 次，且 sub_query_decompose / hyde 目前都简化为
同义词扩展——"策略轮转"实际轮转的是同一个策略。为什么还保留框
架？什么时候值得把 HyDE 真接上 LLM？
----------------------------------------------------------------
【考察点】诚实承认局限 + 演进条件判断。

【参考要点】
- 保留框架的理由：复杂度分析（analyze_query_complexity）+ 策略
  选择 + 轮转记数是一套完整脚手架，真接上 LLM 策略时零结构改
  动，只是填实现——骨架先行的演进式架构。
- 诚实现状：当前重写对检索质量的增益主要来自同义词扩展，复杂
  策略是占位。
- HyDE 接入条件：
  1) 场景匹配：factual 类问题、查询措辞与文档措辞差异大
     （口语问 vs 公文写）时 HyDE 收益最大；
  2) 评估先行：在评估集上证明 recall@k 提升覆盖成本再接；
  3) 成本清醒：每次重写多一次 LLM 调用，且假设答案可能带偏
     检索（幻觉引入检索层）——需要监控改写前后质量分变化。


----------------------------------------------------------------
Q15. 繁体中文：查询转简体用于检索（search_text），但 prompt 组
装用 original_text 原文。为什么不简体统一到底？繁体原文进 prompt
有什么影响？
----------------------------------------------------------------
【考察点】「检索求一致、生成求保真」的分层语言策略。

【参考要点】
- 检索侧统一简体：embedding 和 BM25 索引以简体为主，语义空间
  一致才能召回（繁体查询直接打在简体索引上，分词和向量都会偏）。
- 生成侧保原文：original_text 是文档的原始措辞——专有名词、法
  律条文、合同条款、引文不能被繁简转换污染（转换可能改变专名
  用字，如「著/着」、「台/臺」在专名中的差异）。
- 用简体统一到底的风险：答案里引用的条款措辞与原文不一致，在
  法务/医疗/金融场景是事故。
- LLM 侧影响：主流 LLM 对繁体上下文理解良好，保真成本约等于零；
  且输出语言由 prompt 控制跟随用户语言，体验一致。

四、复杂任务编排（Q16-Q19）

----------------------------------------------------------------
Q16. plan_executor 同层步骤并行执行，共享同一个 AgentState。两个
并行步骤同时写 state，LangGraph 怎么保证不丢数据？写同一个 key
会怎样？
----------------------------------------------------------------
【考察点】LangGraph reducer 机制的实操理解。

【参考要点】
- LangGraph 按 key 的 reducer 合并：声明 Annotated[list,
  operator.add] 的字段（如 step_trace、tool_results）是追加累
  积，并行写不丢；普通字段是**后写覆盖**。
- 本项目设计避开了竞争：并行 PlanStep 的结果先各自进
  tool_results（add 语义安全），由 ResultAggregator 在**并行全部
  完成后**统一聚合写入 rag_docs / db_result / web_docs——单值字
  段不存在并行写。
- 写同一普通 key 的后果：后写覆盖先写，结果不确定（取决于调度
  顺序），是典型坑；防御方法：并行分支只写 add 型字段，汇合节点
  再写单值字段。


----------------------------------------------------------------
Q17. plan_executor（预规划 DAG）和 react_subgraph（Agent 自主循
环）两条复杂路径并存，且 ReAct 默认关闭。适用边界是什么？为什么
不只留一条？
----------------------------------------------------------------
【考察点】确定性/可审计性 vs 灵活性的架构分层。

【参考要点】
- plan_executor：执行前计划全貌已知——步骤、依赖、成本可预估、
  可审计、可复现；适合治理要求高的场景（报告生成、固定业务流
  程、需要 Skill 约束的任务）。
- react_subgraph：边做边看，Agent 根据中间结果决定下一步——适
  合开放探索型问题（路径事先无法规划）；代价是成本不可预测
  （靠预算硬顶）、可审计性弱。
- 不只留一条的原因：治理场景不能容忍 ReAct 的不确定性（财报生
  成必须走受控模板路径）；探索场景 Plan 又规划不出来（第一步
  的结果决定第二步做什么）。
- ReAct 默认关闭 = 能力预埋：灰度可控，问题域验证成熟后再按
  租户开启，是谨慎的能力上线姿势。


----------------------------------------------------------------
Q18. reflection 在 LLM 失败时降级 info_sufficient=True 放行
（fail-open）。如果幻觉校验节点也 fail-open 会怎样？哪些节点
必须 fail-closed，判断标准是什么？
----------------------------------------------------------------
【考察点】按"失败后果可逆性"划分安全等级。

【参考要点】
- fail-open 合理区（体验增强层）：reflection、rerank、跨语言扩
  展、查询重写——它们失败只是答案质量略降，主流程仍能用原始
  结果给出尚可的答案；阻塞反而因小失大。
- 必须 fail-closed（安全关键层）：
  1) 幻觉校验——fail-open = 编造数字静默通过，直接误导决策；
  2) SQL 校验（AST/白名单/LIMIT）——fail-open = 危险 SQL 直达
     生产库；
  3) 报告 verifier 与 publish 门禁——fail-open = 未审核报告
     流出；
  4) 权限/租户隔离。
- 判断标准：失败后果是否可逆、是否对外造成事实性损害。质量下
  降可接受，错误事实不可接受。
- 灰度手法：fail-closed 节点自身故障时的兜底也要设计——幻觉校
  验不可用时应返回保守答案（reject 话术）而不是放行。


----------------------------------------------------------------
Q19. answerability_check 的路由函数里所有 action 都返回
quality_check——目前实际不分流。为什么还留着它？
----------------------------------------------------------------
【考察点】对"先建骨架再填血肉"演进式架构的理解与坦诚。

【参考要点】
- 当前真实价值：它是**度量节点**而非控制节点——coverage_score、
  answerable、recommended_action 全部落进 answerability_result，
  为后续开启分流积累数据（先有分布，再定阈值）。
- 预留的扩展点：react_continue 动作对应"证据不足 → 回流
  react_subgraph 补充取证"的回边，代码注释明确标注暂未实现；
  ask_clarification 对应主动澄清回路。
- 为什么不在没数据时就开分流：阈值拍脑袋会造成误回流（本来够
  用又回去查，成本翻倍）或漏回流；先观察再决策是工程上更稳的
  路径。
- 面试加分句：留下不分流的节点不是冗余，是把"决策权"留给了有
  数据支撑的未来版本。


================================================================
五、幻觉核验与报告治理（Q20-Q23）
================================================================

----------------------------------------------------------------
Q20. 幻觉校验的忠实度怎么算？如果是 LLM 校验 LLM，"用模型防模型
幻觉"是不是循环论证？校验模型自己幻觉了怎么办？
----------------------------------------------------------------
【考察点】识别任务 vs 生成任务的不对称性；分层兜底。

【参考要点】
- 数字类事实走**确定性校验**：从答案中抽取数字/日期/百分比，与
  证据文本做匹配（正则/比对），不依赖模型，无循环论证。
- 语义忠实度确实用 LLM，但不是循环论证，因为任务不对称：
  1) 生成是开放任务（自由发挥空间大，易飘）；校验是封闭识别
     任务（证据就在上下文里，只需判断是否被支持）——识别远易
     于生成，错误率低一个量级；
  2) 校验 prompt 更窄、温度可压到 0、输出结构化（分数），行为
     边界小。
- 校验模型出错的收敛链：MAX_REGENERATES=2 限制重生成次数 →
  exhausted 降级保守答案 → reject 直接拒答——任何一环失败都不
  会导致"幻觉答案无限制流出"。
- 报告链路还有第二道独立校验（verifier 数字↔证据），双保险。


----------------------------------------------------------------
Q21. regenerate 回到 prompt_assembly 而不是直接回 llm_generate。
为什么多走一个节点？第二次生成幻觉率凭什么下降？
----------------------------------------------------------------
【考察点】重生成的有效性来自"输入变化"而非"重新抽奖"。

【参考要点】
- 直接回 llm_generate = 同样输入同样 temperature 重新采样，本
  质是赌运气，第二次大概率犯同样的错。
- 回到 prompt_assembly 的价值：重组装可以改变输入——强化引用
  约束指令、剔除低分/疑似干扰证据、压缩上下文突出高置信证据、
  注入上一轮失败的诊断信息（哪些数字没被支持）。
- 配套机制：regenerate_count 计数，上限 2 次——超过说明不是
  prompt 问题而是证据本身不足，继续重试边际收益为负，应降级
  exhausted 保守答案。
- 一句话：没有输入变化的重生成是赌博，有输入变化的重生成才是
  纠错。


----------------------------------------------------------------
Q22. 报告管线 claim → 血缘 → verifier 的顺序能否调整？verifier
的"数字 ↔ 证据匹配"具体怎么做？10 章节 50 个数字的报告校验成
本是多少？
----------------------------------------------------------------
【考察点】治理管线的依赖关系；治理成本从模型层转移到工程层。

【参考要点】
- 顺序不可调：claim 是校验对象——必须先从章节/图表中抽出"什么
  数字声称了什么事实"并绑定证据（血缘），verifier 才有校验标
  的；没有 claim 就没有 verify 的输入。
- 数字匹配做法（确定性，不用 LLM）：从 claim 文本抽取数值，在
  其绑定的证据文本中检查是否存在/可计算得到（如合计值可由明
  细加总验证）；不匹配即 issue。
- 成本：O(claim 数)，50 个 claim = 50 次字符串/数值比对，毫秒
  级、零 LLM 调用——这是把治理成本从模型层转移到工程层的典型。
- 对比方案：用 LLM 逐条核对 = 50 次调用、分钟级、结果不可复现；
  确定性方案快、便宜、可回归测试。
- 局限要承认：语义级歪曲（数字对但结论错）确定性方法抓不到，
  那是人工审核（publish_status 门禁）兜底的部分。


----------------------------------------------------------------
Q23. draft / pending_review 的报告生成了内容但没有 download_url。
为什么不让草稿也可下载、靠前端权限控制？
----------------------------------------------------------------
【考察点】安全边界画在哪一层；纵深防御。

【参考要点】
- 原则：访问控制应落在**产物层**而不是展示层。前端隐藏按钮但
  API 还在 = 越权访问（broken access control）的经典温床，任何
  会调接口的人都能拿到文件。
- 本项目做法：publish_status ∉ {approved, published} 时导出产物
  但 download_url 置空——对象存储层面就没有可访问链接，越权也
  拿不到东西。
- 审核流转：状态变为 approved 后才生成下载链接，权限与产物同
  步创建。
- 一句话：看不见的按钮防君子，不存在的链接防所有人。

六、架构观与演进（Q24-Q27）

----------------------------------------------------------------
Q24. 项目是 "harness-heavy, model-light"。如果模型能力翻倍（原生
可靠多步工具调用、自带预算意识），harness 里哪些层能拆？哪些永
远不交给模型？
----------------------------------------------------------------
【考察点】区分"因模型弱而存在的补偿层"与"因治理而存在的永恒层"。

【参考要点】
- 可以拆（补偿层）：
  1) JSON action 协议 → 换原生 tool-calling（模型格式可靠性达
     标后，协议税没必要再付）；
  2) 部分自愈脚手架（错误回传的结构化包装，模型原生理解力够
     时可简化）；
  3) 规则路由层可能被更强的 LLM 路由吃掉一部分。
- 永远留（治理层，其价值恰恰在于不随模型行为变化）：
  1) 预算硬约束——模型的"自觉"不能作为成本/延迟的 SLA 保证；
  2) SQL 白名单/AST/LIMIT——安全边界必须确定性；
  3) publish 门禁、verifier——合规与审计要求跟模型智商无关；
  4) 租户隔离、权限校验。
- 一句话：模型越强，harness 里"教模型做事"的部分越少，"不许
  任何人（包括模型）越界"的部分一分不少。


----------------------------------------------------------------
Q25. 全链路 worst case 一共有多少次 LLM 调用？一次请求的成本上
限大概多少 token？有没有端到端成本核算？
----------------------------------------------------------------
【考察点】成本模型的全局量化意识；预算把无界变有界。

【参考要点】
- 逐项点算（worst case）：
  1) 意图路由 LLM 1 次 + Planner 1 次；
  2) SQL Agent ≤10 次（预算上限）；
  3) ReAct 子图（如开启）：受其 LLM 预算上限约束；
  4) reflection 1 次（5s 超时降级）；
  5) llm_generate 1 次；
  6) 幻觉校验 1 次 + regenerate ×2（每次再 generate+verify，
     ≈4 次）；
  7) 报告场景：每章节 1 次生成（章节数 × 1）。
  → 问答 worst case ≈ 15-20 次；报告场景 20-30+ 次。
- token 量级：单次调用输入 1-4k token（prompt+证据），worst case
  总消耗数万 token 量级——每租户需要计量分账。
- 关键设计意义：预算体系的价值就是把"理论上无界的 agent 循环"
  变成"可定价的有界调用"，成本上限 = Σ(各环节预算 × 单次成本)，
  可事先向业务方报价。
- 现状坦诚：端到端成本核算/分账是待补能力（observability 节点
  已有计时，token 计量是下一步）。

Q26. 如果现在重构这个项目，你最想改掉的一个设计是什么？
----------------------------------------------------------------
【考察点】诚实度 + 优先级判断 + 修复路径（背简历的人答不出）。

【参考要点】（任选其一，附修复路径）
- 首选候选：rerank_score 与 similarity 混用同一质量阈值（Q13）
  ——开关 rerank 导致相关性判定漂移，质量监控出现假波动；
  修复：按 scorer 分校准阈值或统一归一化口径，评估集回归验证。
- 其他合理候选：
  1) hybrid 串行 → 借 plan_executor 并行化（Q4），延迟砍半；
  2) answerability_check 有名无实（Q19）→ 先跑数据再开分流；
  3) HyDE/子查询拆解接 LLM（Q14）→ 评估集证明收益后启用；
  4) quality_check 阈值硬编码 → 下沉到配置文件按租户可调。
- 答题结构：是什么 → 为什么是它（影响面）→ 怎么改 → 怎么验证
  改对了。


----------------------------------------------------------------
Q27.（压力题）线上反馈：某查库问题偶尔返回"确认无数据"，但业务
方说数据明明存在。从 verdict 链路倒推，按什么顺序排查？
----------------------------------------------------------------
【考察点】把 verdict 语义链完整倒出来的排障方法论。

【参考要点】（排查顺序）
1) 调 step_trace 看 Agent 实际探索路径：list_tables 看到目标表
   了吗？describe 的是正确的表吗？（可能选错库/选错表）
2) 看幻觉护栏日志：describe 是否因表名不在披露清单被拒绝过？
3) 看最终 SQL 语义：WHERE 条件是否过严（时间范围、状态字段、
   租户条件）、列名是否选对、JOIN 是否丢数据——"偶尔"二字指向
   SQL 语义边界（某些条件下才查空）；
4) 确认 verdict 来源：是 Agent 主动 finish(no_data) 还是 SQL
   成功但空结果的兜底判定——前者是模型判断问题，后者是 SQL
   问题；
5) 检查是否预算提前耗尽：预算紧张时 Agent 浅尝辄止，没探到
   正确的表就收尾；
6) 检查模板短路：source=template 时 Agent 根本没运行——模板
   误命中 + 模板 SQL 语义过时 = 稳定复现"确认无数据"；
7) 修复对应：探索路径问题 → 注入 exploration_hints；SQL 问题
   → 业务规则进 prompt；模板问题 → 模板治理/下线路径；预算问
   题 → 调预算或优化表披露顺序。

七、实战排障（Q28）

----------------------------------------------------------------
Q28. 向量库明明录入了一份退货流程文档，用户问"如何退货"却没检索
出来。如何排查？问题可能出在哪？
----------------------------------------------------------------
【考察点】沿「入库 → 路由 → 检索 → 排序 → 后处理」五关卡逐段
定位，不要一上来怀疑向量模型。

【参考要点】
排查顺序（五关卡法）：

关卡 1：文档真的进库了吗（最常见的坑，"录入了"≠"可检索"）
- 解析状态是否 DONE（DeepDoc 解析 PDF 可能失败/卡住）；
- chunk 质量：chunk 数为 0？OCR 乱码？表格被切碎？"退货流程"
  被拆到两个 chunk？
- 文档是否被 disabled；
- 入库后是否换过 embedding 模型（老向量在旧语义空间，新查询在
  新空间，永远对不上，且状态显示正常——最隐蔽）。
- 快速验证：用文档原文一句话在知识库检索测试里搜，搜不到 =
  入库环节问题。

关卡 2：请求真的走到 RAG 了吗（路由层拦截）
- 看日志 route_target："退货"像业务词，可能被误判 database /
  chitchat，根本没进 rag_tool；
- kb_ids 是否传对：为空时 RAGTool 静默返回空结果，不报错；
- 多 KB embedding 模型一致性：代码有硬断言 assert len(embd_nms)
  == 1，混用直接异常走空；
- tenant 解析：actual_tenant_id 不对时权限过滤把 chunk 全滤掉。

关卡 3：检索层——关键词和向量谁失灵（对照实验）
- keywords_similarity_weight=1.0 单测 → BM25 侧：中文分词是否
  切对"退货"？文档写"退换货/退回商品"而查询是"退货"，分词无
  交集 → BM25 失灵；
- weight=0.0 单测 → 向量侧：查询仅 4 字语义稀薄 vs 流程长文，
  相似度天然偏低；
- similarity_threshold=0 再查：能搜到但分低 → 混合后被 0.2 阈
  值截断（典型场景：BM25 0 分 + 向量 0.35×0.5=0.175 < 0.2）。

关卡 4：排序层——检到了但被挤掉
- top_k=5 截断：目标 chunk 排第 6 被切掉；
- rerank 帮倒忙：模型对该领域不熟把相关 chunk 排到后面；或
  rerank 失败静默 fallback（只有 warning 日志）；
- rerank_score 与 similarity 混用 0.5 阈值：开关 rerank 后相关
  性判定漂移（见 Q13）。

关卡 5：后处理层——检出来了但没进答案
- 质量评估拦截：score < 0.5 → has_relevant=False → 内部重搜仍
  失败 → quality_check retry/fallback_web，最终答案来自 Web
  兜底而非知识库；
- prompt 截断：前 5 条 × 500 字，目标 chunk 被截掉；
- LLM 没用上：chunk 在 prompt 末尾被忽略。

根因概率排序（实战）：
1) 文档解析/分块质量差；
2) 入库后换过 embedding 模型；
3) 查询与文档措辞不匹配 + 权重混合后低于阈值；
4) 意图路由误判；
5) kb_ids 传错/为空；
6) 多 KB embedding 冲突；
7) top_k / rerank / 质量阈值拦截。

修复对应：
- 入库侧：重解析/调 chunking；换模型必须重建索引；
- 检索侧：短查询同义扩展（"退货"→"退货/退换货/退回商品/退款"）、
  调阈值/权重、评估后上 HyDE；
- 工程侧：空结果加显式告警区分"kb_ids 为空"与"检索为空"；监控
  rerank 失败率；
- 路由侧：bad case 回流校准规则关键词表。

一句话版：沿链路倒查，先验证入库质量，再确认路由与参数，再用
关键词/向量单测+阈值清零定位召回还是截断，最后查排序与后处理；
八成问题出在前两关——"录入了"不等于"可检索"，"到 rag_tool 了"
不等于"参数对了"。

附：答题通用原则
================================================================
1) 承认局限是加分项：Q13/Q14/Q19/Q26 都在考"能不能指出自己系统
   的缺陷"——面试官更信能讲清伤口的人。
2) 每个设计决策都要能答出"不这么做的替代方案是什么、为什么没选"。
3) 数字要熟：0.7 路由阈值 / 0.5 相关阈值 / 0.7 质量阈值 /
   0.85-0.6-0.4 幻觉三档 / 预算 10-10-4-6-90 / MAX_REGENERATES=2 /
   MAX_INTERNAL_RETRIES=1 / LIMIT 500 / 表截断 200 / top_k 5。
4) 任何"防幻觉/防失控"问题，先答确定性工程手段，再答 LLM 手段
   ——顺序体现工程品味。
