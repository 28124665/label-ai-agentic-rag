# 工具调用体系可扩展性改造方案

> 状态：草案（待评审）
> 日期：2026-09-04
> 范围：`agent/langgraph/tools/`、`agent/langgraph/executor/`、`agent/langgraph/state.py`
> 原则：不推倒重来，三步渐进式演进，每步独立验收、独立回滚

## 1. 背景与目标

工具体系从最初的 RAGTool，逐步扩展出 DatabaseTool、WebTool、RestTool、ReportTool，未来还将新增 GraphTool（已具雏形，未接入分发）、WikiTool 等。随着工具数量持续增长，现有「if/elif 硬编码分发 + 各工具返回字段平铺」的结构熵增加剧：

- 新增一个工具要改 **分发器、`ToolResult` 字段、消费方判断** 多处；
- 各工具返回 dict 字段形状迥异（`rag_docs` / `db_result` / `web_docs` / `rest_result` / `report_artifacts`），上游到处写 `if "rag_docs" in r elif "db_result" in r`。

**目标**：以「新增工具仅需一次注册 + 一个 `_do_execute` 实现 + 一份配置」为最终形态，收敛改动面，保障可扩展性与稳定性，且**不改变现有行为**。

## 2. 现状分析

### 2.1 已具备的优良范式（作为推广范本）

| 现状 | 范式 | 位置 |
|------|------|------|
| `GatewayResolver` 按租户/模式解析网关 | 策略模式 + 工厂 + 依赖注入 | `agent/langgraph/gateways/factory.py` |
| `ModelGateway` Protocol，统一 8 个 LLM 调用点 | 面向接口编程（`runtime_checkable`） | `agent/langgraph/gateways/model.py` |
| `SkillRegistry` 不可变快照、原子替换、O(1) 索引 | 注册表 + 快照 | `agent/langgraph/skills/registry.py` |

### 2.2 最大坏味道：硬编码分发

`agent/langgraph/executor/tool_dispatcher.py#L54-L65`：

```python
if step.tool == "rag":
    result = await self._execute_rag(step, state)
elif step.tool == "database":
    result = await self._execute_database(step, state)
elif step.tool == "web":
    result = await self._execute_web(step, state)
elif step.tool == "report":
    result = await self._execute_report(step, state, previous_results)
elif step.tool == "rest":
    result = await self._execute_rest(step, state)
else:
    raise ValueError(f"未知工具类型: {step.tool}")
```

### 2.3 第二个坏味道：返回字段平铺

`ToolResult`（`agent/langgraph/state.py#L27-L74`）将所有工具特有字段平铺进一个大 TypedDict：

```python
class ToolResult(TypedDict, total=False):
    step_id: str
    tool: str
    success: bool
    error: str
    # RAG 特有
    rag_docs: list[dict]
    rag_quality_score: float
    rag_has_relevant: bool
    rag_relevant_count: int
    rag_top_score: float
    # DB 特有
    db_result: dict
    db_quality_score: float
    db_id: str
    # Web 特有
    web_docs: list[dict]
    # REST 特有
    rest_result: dict
    rest_quality_score: float
    rest_endpoint: str
    rest_method: str
    erp_domain: str
    # Graph 特有（字段已预留，dispatcher 尚未接入）
    graph_result: dict
    graph_quality_score: float
    graph_score_source: str
    ...
```

代价：每新增一个工具，就要往 `ToolResult` 追加一组 `xxx_*` 前缀字段，且所有消费方（`quality_check`、evidence 归一化、反思）都通过「前缀判断」识别结果来源。

### 2.4 现状各工具返回字段清单

| 工具 | dispatcher 方法 | 返回字段 |
|------|----------------|---------|
| rag | `_execute_rag` L98 | `rag_docs` / `rag_quality_score` / `rag_has_relevant` / `rag_relevant_count` / `rag_top_score` / `kb_ids` / `retrieval_error_code` / `retrieval_mode_used` / `rag_score_source` / `rag_avg_score` / 等 |
| database | `_execute_database` L202 | `db_result` / `db_quality_score` / `db_id` |
| web | `_execute_web` L363 | `web_docs` |
| rest | `_execute_rest` L386 | `rest_result` / `rest_quality_score` / `rest_endpoint` / `rest_method` / `erp_domain` |
| report | `_execute_report` L440 | `report_artifacts` / `report_summary` / `report_quality_score` / `report_error` / 等 |

## 3. 设计原则

| 原则 | 在本方案中的落点 |
|------|-----------------|
| 开闭原则（OCP） | 新增工具不改 dispatcher、不改 `ToolResult`、不改 graph |
| 依赖倒置（DIP） | 上层依赖 `Tool` 抽象，不依赖具体工具类 |
| 接口隔离（ISP） | `Tool` 只暴露 `invoke` 一个入口，类型特有数据进 `payload` |
| 单一职责（SRP） | 分发、生命周期、执行逻辑分层解耦 |
| 无行为变化 | 三步重构期间，对外行为与返回字段兼容 |

## 4. 目标架构

```
PlanStep (step.tool)
      │
      ▼
ToolRegistry.dispatch(name)          ← 策略 + 注册表（替代 if/elif）
      │
      ▼
BaseTool.invoke(input, ctx)          ← 模板方法（统一骨架：校验→执行→后处理→兜底）
      │
      ├─ _validate()                  hook
      ├─ _do_execute()                abstract（各工具唯一需要实现的方法）
      └─ _post_process()              hook
      │
      ▼
ToolOutcome                          ← 统一契约（公共字段 + payload）
      │
      ▼
to_state_fields()                    ← 过渡期适配器，展平回旧字段，消费方零改动
```

分层职责：

- **契约层**：`Tool` Protocol、`ToolContext`、`ToolOutcome`（新增，不接业务）。
- **注册层**：`ToolRegistry` + `@register_tool`（新增，替代 if/elif）。
- **生命周期层**：`BaseTool` 模板方法（新增，收敛 try/except + latency + 透传）。
- **适配层**：`ToolOutcome.to_state_fields()` 反向展平，兼容现有消费方。

## 5. 三步改造方案

### 5.1 第一步：抽 `Tool` Protocol + 统一 `ToolOutcome`（无行为变化）

**应用模式**：面向接口编程 + 依赖倒置（DIP）；统一数据契约（DTO）；过渡期用适配器。

**目标**：建立统一契约，先不改任何工具实现、不改 dispatcher 分支、不改消费方。

**改动点**：新增 `agent/langgraph/tools/contract.py`（或 `base.py`）。

**关键骨架**：

```python
"""Tool 统一契约（第一步新增，暂不接业务）。"""
from __future__ import annotations

from dataclasses import dataclass, field
from typing import Protocol, runtime_checkable


@dataclass(frozen=True)
class ToolContext:
    """从 AgentState 提取的请求级上下文，供各工具统一取参。

    由 dispatcher 填充，避免每个工具各自从 state 里挖字段。
    """
    tenant_id: str = ""
    kb_ids: list[str] = field(default_factory=list)
    llm_id: str = ""
    query_lang: str = "zh_CN"
    agent_config: dict = field(default_factory=dict)


@dataclass
class ToolOutcome:
    """工具统一返回对象（新契约）。

    - 公共字段：质量评估 / 证据归一化 / 反思统一消费；
    - payload：承载类型特有数据，公共层不感知。
    """
    success: bool = True
    tool: str = ""
    error_code: str = ""
    error: str = ""
    latency_ms: int = 0

    # 公共语义字段
    docs: list[dict] = field(default_factory=list)
    quality_score: float = 0.0
    has_relevant: bool = False
    relevant_count: int = 0

    # 类型特有数据（如 db_result / rest_result / report_artifacts）
    payload: dict = field(default_factory=dict)

    def to_state_fields(self) -> dict:
        """过渡期适配器：展平回旧的 xxx_* 平铺字段。

        保证第一步不改消费方，第二步/第三步后按需裁剪。
        """
        out = {
            "success": self.success,
            "tool": self.tool,
            "error": self.error or "",
            "error_code": self.error_code,
            "latency_ms": self.latency_ms,
        }
        # 公共语义字段先按 RAG 命名回填（兼容现有消费方）
        if self.tool in ("rag", "web", "database", "rest"):
            out[f"{self.tool}_quality_score"] = self.quality_score
        out.update(self.payload)
        return out


@runtime_checkable
class Tool(Protocol):
    """工具统一入口协议。

    上层只依赖此抽象，不依赖 RagTool / DatabaseTool 等具体类。
    """
    name: str

    async def invoke(self, input_data: dict, *, ctx: ToolContext) -> ToolOutcome: ...
```

**兼容策略**：本步**只新增契约文件**，不改任何现有工具与 dispatch 分支，`ToolResult` TypedDict 暂不删除 `xxx_*` 字段。新旧并存，新契约先「存在」，供第二步/第三步接入。

**验收标准**：
- [ ] 新增 `contract.py` 可通过 `python -m py_compile`；
- [ ] 现有 5 个工具、dispatcher、消费方**零改动**，全量回归无行为差异；
- [ ] `Tool` Protocol 可被 `isinstance` 校验（`runtime_checkable`）。

### 5.2 第二步：引入 `ToolRegistry` + `@register_tool`

**应用模式**：策略模式 + 注册表 / 服务定位器；装饰器做自注册。

**目标**：消灭 `tool_dispatcher.dispatch` 的 `if/elif` 链条，新增工具从「改 dispatcher」变为「注册一次」。

**改动点**：
- 新增 `agent/langgraph/tools/registry.py`；
- 每个工具类标注 `@register_tool("xxx")`；
- `ToolDispatcher.dispatch` 改为 `registry.dispatch`。

**关键骨架**：

```python
"""工具注册表（第二步）。"""
from __future__ import annotations

from agent.langgraph.tools.contract import Tool, ToolContext

_REGISTRY: dict[str, Tool] = {}


def register_tool(name: str):
    """装饰器：将工具类实例化后注册进全局表。"""
    def decorator(cls):
        _REGISTRY[name] = cls()
        return cls
    return decorator


class ToolRegistry:
    def get(self, name: str) -> Tool | None:
        return _REGISTRY.get(name)

    async def dispatch(self, name: str, input_data: dict, *, ctx: ToolContext):
        tool = _REGISTRY.get(name)
        if tool is None:
            raise ValueError(f"未知工具类型: {name}")
        return await tool.invoke(input_data, ctx=ctx)


def get_tool_registry() -> ToolRegistry:
    return _REGISTRY_SINGLETON
```

改造后的 `dispatch`（`tool_dispatcher.py`）：

```python
async def dispatch(self, step, state, previous_results):
    registry = get_tool_registry()
    ctx = self._build_context(state)
    try:
        outcome = await registry.dispatch(step.tool, self._build_input(step, state), ctx=ctx)
        result = outcome.to_state_fields()
        result["step_id"] = step.step_id
        return ToolResult(**result)
    except Exception as e:
        # 单步异常隔离（原有语义保留）
        return ToolResult(step_id=step.step_id, tool=step.tool,
                          success=False, error=str(e),
                          error_code="TOOL_EXECUTION_FAILED",
                          latency_ms=...)
```

新增 `wikitool` 只需：

```python
@register_tool("wiki")
class WikiTool:
    name = "wiki"
    async def invoke(self, input_data, *, ctx) -> ToolOutcome:
        ...
```

**验收标准**：
- [ ] `dispatch` 内不再出现 `step.tool == "..."` 分支；
- [ ] 新增/移除一个工具仅涉及一个注册声明，不改 `dispatch`；
- [ ] 未知工具名仍抛 `ValueError`（快速失败语义保留）；
- [ ] 单步异常隔离、`step_id/tool/success/latency_ms` 透传行为不变。

### 5.3 第三步：抽 `BaseTool` 模板方法

**应用模式**：模板方法 + 钩子方法（`_validate` / `_post_process`）。

**目标**：把 dispatcher 里「try/except + latency 计时 + 统一错误码 + 返回 ToolOutcome」这段在 5 个工具中重复的逻辑下沉到基类，子类只实现 `_do_execute`。

**改动点**：新增 `agent/langgraph/tools/base.py`，各工具类改为继承 `BaseTool`，删除各工具内重复的异常/计时逻辑。

**关键骨架**：

```python
"""工具生命周期基类（第三步）。"""
from __future__ import annotations

import time
from abc import ABC, abstractmethod

from agent.langgraph.tools.contract import ToolContext, ToolOutcome


class BaseTool(ABC):
    name: str = ""

    async def invoke(self, input_data: dict, *, ctx: ToolContext) -> ToolOutcome:
        started = time.perf_counter()
        try:
            self._validate(input_data)                          # 钩子1
            outcome = await self._do_execute(input_data, ctx)   # 抽象：可变步骤
            outcome.success = True
            outcome = self._post_process(outcome)               # 钩子2
        except ToolUnavailable as e:                            # 外部系统不可用→降级
            outcome = ToolOutcome(success=False, error_code="TOOL_UNAVAILABLE", error=str(e))
        except Exception as e:                                  # 统一兜底
            outcome = ToolOutcome(success=False, error_code="TOOL_EXECUTION_FAILED", error=str(e))
        outcome.tool = self.name
        outcome.latency_ms = int((time.perf_counter() - started) * 1000)
        return outcome

    @abstractmethod
    async def _do_execute(self, input_data: dict, *, ctx: ToolContext) -> ToolOutcome:
        """各工具唯一必须实现的方法。"""

    def _validate(self, input_data: dict) -> None:
        """默认空实现，子类按需覆盖。"""

    def _post_process(self, outcome: ToolOutcome) -> ToolOutcome:
        """默认透传，子类按需覆盖（如统一质量评估）。"""
        return outcome
```

改造后，`WikiTool` 仅需实现 `_do_execute`：

```python
@register_tool("wiki")
class WikiTool(BaseTool):
    name = "wiki"

    async def _do_execute(self, input_data, *, ctx) -> ToolOutcome:
        docs = await self._search(input_data["query"])
        return ToolOutcome(docs=docs, quality_score=..., payload={...})
```

**验收标准**：
- [ ] 5 个工具类均继承 `BaseTool`，只保留 `_do_execute` 及其特有逻辑；
- [ ] `try/except`、`latency_ms`、`error_code`、`ToolOutcome` 组装逻辑仅存在于基类；
- [ ] 业务失败（返回 `success=False` 的结果）与外部系统异常（抛 `ToolUnavailable`）语义区分；
- [ ] 全量回归无行为差异。

## 6. 稳定性保障

| 保障 | 措施 |
|------|------|
| 异常隔离 | 单工具失败不影响其它步骤（`dispatch` 外层 catch 保留） |
| 快速失败 | 未知工具名、外部系统不可用显式抛错，禁止静默降级 |
| 统一可观测 | `success / error_code / latency_ms` 收敛进 `ToolOutcome`，metrics/日志消费统一字段 |
| 错误分类 | 区分「业务失败」与「外部系统不可用（`TOOL_UNAVAILABLE`）」，后者触发降级而非无脑重试 |
| 预算与配额 | 按工具 `category` 分配 token/配额，新工具默认继承上限（对齐现有 `token_budget` / `database/budget`） |
| 配置外置 | 工具启用开关、参数阈值放 `config`，新增工具不改代码即可开关 |
| 快照原子替换 | 注册表 reload 失败保留旧实例（对齐 `SkillRegistry` 约束3） |

| 步骤 | 新增 | 修改 | 删除 | 消费方影响 |
|------|------|------|------|-----------|
| 第一步 | `tools/contract.py` | 无 | 无 | 零 |
| 第二步 | `tools/registry.py` | `executor/tool_dispatcher.py`（dispatch 改查表） | 无 | 零（经 `to_state_fields` 兼容） |

**兼容红线**：三步期间 `ToolResult` 的 `xxx_*` 平铺字段不删除、不改名；`to_state_fields()` 保证消费方（`quality_check`、evidence 归一化、反思、报告生成）零改动。

## 8. 测试策略

1. **单元测试**：`ToolRegistry` 注册/分发/未知工具名抛错；`BaseTool` 的异常兜底与 `latency_ms` 计时。
2. **回归测试**：三步各自完成后，运行 `uv run pytest` 全量回归，确认 5 个工具行为无差异。
3. **契约测试**：`isinstance(tool, Tool)` 校验所有已注册工具满足 Protocol。
4. **扩展性验证**：新增一个 mock `WikiTool`，验证仅需「注册 + `_do_execute` + 配置」三处改动即可接入。

## 9. 风险与回滚

| 风险 | 缓解 |
|------|------|
| `ToolResult` 字段形态改动波及消费方 | `to_state_fields()` 适配层保证零改动；先加不删，兼容过渡 |
| 工具类改动引入行为差异 | 三步分离、每步独立回归，任一步失败回滚该步 |
| `Protocol` 静态检查与运行时语义不一致 | 保留 `runtime_checkable`，dispatch 前做 `isinstance` 校验 |
| 过度抽象、为模式而模式 | 严格按三步走，第二步/第三步仅在工具数增长、if/elif 达 3+ 分支时推进 |
