# RAG 性能优化建议（Task 11）

> 本文档基于 `test/perf/reports/baseline_report.md` 的基线测试结果，针对二期 RAG 增强链路中的性能瓶颈给出可执行的优化建议。
> 对应需求：PRD Phase 2 `P2-NFR-01`。

## 1. 基线报告关键瓶颈

| 序号 | 瓶颈点 | 关键证据 | 对目标的影响 |
|------|--------|----------|--------------|
| 1 | **Rerank 延迟随并发明显上升** | stable-50 阶段 P95（5,800 ms）较 stable-10（3,450 ms）上升约 68% | 拉高单次检索与复杂查询端到端延迟，接近 P95 < 5,000 ms 目标 |
| 2 | **突发流量下超时率上升** | burst 阶段超时率达到 1.00%，达到 SLA 上限 | 存在突破超时率 < 1% 目标的风险 |
| 3 | **复杂查询 LLM 首 token / 整体延迟偏高** | complex 查询 P95 9,200 ms，接近 10,000 ms 阈值 | 复杂查询 P95 < 10,000 ms 目标余量不足 |
| 4 | **整体 P95 随 QPS 线性恶化** | 整体 P95 从 stable-10 的 3,450 ms 升至 stable-50 的 5,800 ms | 高并发下用户体验波动大 |

## 2. 性能目标（Task 11 达标线）

| 指标 | 目标值 | 基线表现 | 达标状态 |
|------|--------|----------|----------|
| 简单查询 P95 | < 2,000 ms | 1,150 ms | ✅ 已达标 |
| 单次检索 P95 | < 5,000 ms | 4,800 ms | ✅ 已达标，余量小 |
| 复杂查询 P95 | < 10,000 ms | 9,200 ms | ✅ 已达标，接近阈值 |
| 错误率 | < 1% | 0.50% | ✅ 已达标 |
| 超时率 | < 1% | 0.76% | ✅ 已达标，接近阈值 |

> 基线整体已达标，但高并发与突发流量下余量不足。执行以下优化后可提升冗余度，确保生产环境稳定达标。

## 3. 针对性优化建议

### 3.1 缓存优化

| 优化项 | 现状问题 | 具体措施 | 预期收益 |
|--------|----------|----------|----------|
| **Embedding 查询缓存扩容** | 重复查询 embedding 调用耗时 | 将 Redis LRU Embedding 缓存容量从默认配置提升至 50,000 条，命中率目标 ≥ 85%；对相同 query 的向量在 TTL 内复用 | 降低检索阶段 P95 10%–20% |
| **检索结果缓存** | 高频 FAQ 类问题重复检索 | 对简单查询（query 长度 ≤ 15 字且为 FAQ 意图）增加 30s 本地 + Redis 二级缓存，缓存 key 包含 kb_id + query_hash | 降低简单查询 P95 20%–30% |
| **Rerank 分数缓存** | 相同 (query, doc) 对重复打分 | 对 Rerank 输入对做哈希缓存，TTL 60s；仅缓存 score ≥ 0.5 的高频对 | 降低 Rerank 重复计算 15%–25% |
| **Prompt 模板编译缓存** | LLM prompt 反复格式化 | 对 Grader / 幻觉检测 prompt 模板使用 `functools.lru_cache` 编译后缓存 | 减少单次 LLM 调用 CPU 开销 |

### 3.2 并发控制与资源池化

| 优化项 | 现状问题 | 具体措施 | 预期收益 |
|--------|----------|----------|----------|
| **HTTP 连接池复用** | 每次请求新建 TCP 连接 | 在 `requests` 调用处使用 `requests.Session()` 并设置 `pool_connections=20, pool_maxsize=100` | 降低连接建立延迟，减少突发流量超时 |
| **LLM 请求池化 / 限流** | 突发流量导致 LLM 排队 | 在 LLM 调用层增加异步请求池（sem=50）+ 滑动窗口限流（RPM/TPM），队列满时直接触发降级 | 降低超时率，保护 LLM 配额 |
| **Rerank 批量推理** | 单条 doc 多次调用模型 | Rerank 服务支持 batch_size=16/32 批量推理；Agent 链路中收集 top_k docs 后一次性送入 | 降低 Rerank P95 30%–40% |
| **Grader 批量大小调整** | 默认 batch_size=5 可能 LLM 调用次数过多 | 对长 query 或短 doc 场景使用 batch_size=8–10（不超过 10），同时控制 `max_eval_tokens` | 减少 Grader LLM 调用次数，降低 P95 |

### 3.3 模型与算法选择

| 优化项 | 现状问题 | 具体措施 | 预期收益 |
|--------|----------|----------|----------|
| **Grader 轻量模型兜底** | LLM 评估延迟高、配额受限 | 默认使用本地轻量级 NLI/Cross-Encoder，仅在置信度低时调用 LLM；LLM 评估超时 10s 后 fallback 到 Rerank | 降低 Grader P95 至 < 1,000 ms |
| **幻觉检测分层剪枝** | 每条 claim 都走 LLM，成本高 | 规则层先判定数值/日期/比例，SUPPORTED 的 claim 跳过模型层；仅规则层为 neutral 时调用 NLI/LLM | 降低幻觉检测 P95 20%–30%，控制 Token 成本 |
| **Rerank 模型量化** | 大模型推理慢 | 对 Cross-Encoder 做 INT8 量化或切换至更小的 `bge-reranker-v2-m3` | 提升 Rerank 吞吐量 2–3 倍 |
| **查询重写策略裁剪** | HyDE 默认关闭但仍需评估开销 | 保持 `enable_hyde=False`（默认）， synonym_rewrite 使用规则模板而非 LLM，子查询拆解限制 `sub_query_max_count=3` | 降低重试阶段 Token 与延迟 |

### 3.4 检索参数调整

| 优化项 | 现状问题 | 具体措施 | 预期收益 |
|--------|----------|----------|----------|
| **ES 分片与副本** | 默认分片数不适合 50K 文档规模 | 50K 文档知识库设置 `number_of_shards=3, number_of_replicas=1`；避免过多小分片 | 降低检索 P95 15%–25% |
| **混合检索动态权重** | 向量/BM25 权重固定，长尾查询慢 | 短查询（≤10 字）提高 BM25 权重至 0.7；长查询提高向量权重至 0.8 | 减少向量检索计算量，降低简单查询延迟 |
| **Top-K 截断策略** | 召回过多 doc 导致 Rerank 负担重 | 检索召回 top_k=30，Rerank 后取 top_k=10；Grader 仅评估 Rerank 后的 top 10 | 降低 Rerank + Grader 总耗时 |
| **ES 查询 DSL 优化** | 复杂 bool 查询存在冗余 should 子句 | 合并同义 should 子句，使用 `minimum_should_match=1`；对 filter 条件使用 `constant_score` | 降低 ES 查询耗时 10%–20% |

### 3.5 网络超时与降级

| 优化项 | 现状问题 | 具体措施 | 预期收益 |
|--------|----------|----------|----------|
| **分阶段超时控制** | 全局 60s 超时粒度粗 | 检索 5s、Rerank 3s、Grader 10s、LLM 生成 30s；子阶段超时触发降级而非整体失败 | 降低整体超时率，提升可观测性 |
| **熔断器参数校准** | 突发失败时持续重试 | 按 P2-NFR-02 配置：LLM 5 次失败/60s 熔断、Rerank 3 次/30s、ES 5 次/60s | 防止级联故障，降低错误率 |
| **主动健康检查** | 依赖服务已异常仍发送请求 | `api/utils/health_checker.py` 每 10s 探测，异常时提前熔断并走降级路径 | 减少无效调用，降低错误与超时 |
| **降级响应缓存** | 降级后仍重复计算 | ES 不可用时返回最近 1 小时内的缓存结果（如有），并标记 `degraded=true` | 提升降级场景可用性 |

## 4. 优化优先级与落地顺序

| 阶段 | 优化项 | 优先级 | 依赖 |
|------|--------|--------|------|
| 第 1 周 | Embedding 缓存扩容、HTTP 连接池、Top-K 截断 | P0 | 无 |
| 第 1 周 | Rerank 批量推理 + 模型量化 | P0 | Rerank 服务支持 batch |
| 第 2 周 | Grader 轻量模型兜底、幻觉检测分层剪枝 | P1 | 已实现的 Grader/幻觉检测组件 |
| 第 2 周 | ES DSL 优化、分片调整、混合检索动态权重 | P1 | ES 管理员权限 |
| 第 3 周 | LLM 请求池化/限流、分阶段超时、熔断校准 | P1 | `api/utils/circuit_breaker.py` |
| 第 3 周 | 检索结果缓存、Rerank 分数缓存、降级响应缓存 | P2 | Redis |

## 5. 验收检查项

- [ ] stable-50 阶段整体 P95 < 5,000 ms（单次检索目标）
- [ ] complex 查询 P95 < 10,000 ms 且余量 ≥ 500 ms
- [ ] 错误率 < 1%、超时率 < 1%（稳定与突发阶段均满足）
- [ ] 降级触发率 < 5%
- [ ] Rerank P95 < 1,000 ms（50 条文档）
- [ ] Grader P95 < 2,000 ms（10 条文档）
- [ ] 幻觉检测 P95 < 3,000 ms
